## Acceptance criteria

- [ ] 每次插件调用统一统计实际模型、工具、耗时及 token 用量；本轮所有模型请求都经过同一计数入口。
- [ ] 调用前检查预算，达到限制后不再真实请求模型或执行工具；耗尽原因与实际计数对外可见。
- [ ] 同批工具中途达到限制时尾部调用不产生副作用，仍得到明确未执行配对结果；占位结果不计为真实成功调用。
- [ ] 保留重复调用、连续工具错误及工具观察长度保护，最终结束原因为 budget_exhausted 或对应明确保护结果。
- [ ] 对 Pi 0.6.0 的请求前检查及批次末停止进行集中薄适配，保留基类准备/持久化逻辑，不复制核心循环。
- [ ] 用契约测试证明版本、回调顺序、工具配对和批次末停止，不能以单个 terminate 结果假定整批已停止。
- [ ] 预算内恢复不重置统计；新的插件调用有新的运行预算，前轮统计及原业务引用仍可追溯。
- [ ] 两种输出策略展示一致计数和结束原因；保存已完成项后结束，不隐瞒新增失败或错误输出。

## Implementation context

- 按已确认规格实施：社区 Python Pi core/harness 0.6.0 为初始基线，单项目单插件双入口；Dify 持有模型/工具授权与唯一跨轮状态。内部只提供认知工具，不恢复已移除能力。
- 模型摘要与溢出重试在 10 加入时必须使用本票统一计数；确认恢复在 11 接入同一策略/预算检查。
- 正常停止不能在自身被 await 的 hook 中调用会自等待的 abort；如需大范围改写社区核心，回到规格约定的设计评估。
