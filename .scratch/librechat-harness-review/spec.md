# 借鉴 LibreChat 的 Dify 执行内核可靠性设计

Status: implemented — validated and reviewed

2026-10-28：用户确认建议并调用 `/implement`，授权实施以下已收敛范围，在当前分支完成验证、审查和提交。

## 实施与验收范围

1. 模型消息投影与预算一致；完整 UI output 不重复进入持久模型历史。当前调用和中断恢复需要的信息继续保留。
2. 修复尾部工具组切点、完整摘要替换和固定上下文提前拒绝；旧结果按压力缩减，摘要从仍保留的缩减前内容生成；改善中英混合估算。
3. 同批工具结果先完整配对，再注入 Skill 正文；中断后未执行尾部有明确配对结果与事件收尾。
4. SkillReadResource 连续有界分页，页大小与单条/批次预算协调，返回实际区间及下一位置。保持技能路径检查，不增加通用文件工具。
5. 技能入口资格生效，已加载记录能识别定义变化或不完整摘要并重新加载完整指令。工具仍全量展示，Skill 优先仍由提示驱动。
6. 状态编码最终容量检查；容量足够时不误删任务，无法保留完整 pending 时显式失败；异常补齐安全的 agent_failed JSON 和运行/阶段关联。
7. README 与本目录记录最终行为和验证。流式参数累计/增量兼容、代码环境、通用原始结果缓存、外部 MCP 接口改造、排队与前端改造均不在本轮。

沿此前报告已约定的公开边界做行为回归：AgentLoop 的实际模型输入、工具执行/结果与最终历史；ToolAdapter 的技能资源读取；DifyStateBackend/状态 codec；runtime/strategy 的两种协议输出。模型、Dify SDK、工具调用及文件系统是 fake/临时文件边界，不 mock 自有核心协作者或单测私有 helper。每项缺陷先红后绿，最后运行完整后端套件、增量类型检查与离线打包验证。

## 用户问题：当前环境能否导出

仓库 CT MCP 元数据夹具包含 `export_people_excel`、`export_appointment_forms`、`get_export_job`；普通模型工具可进入 MCP 工具目录。已有 Dify 工具产物输出路径及直连 MCP blob 转发路径，前端支持附件展示和下载。

这证明当前架构具备消费外部导出能力，不证明生产环境配置了这些服务，也不证明导出接口、业务权限、异步查询和下载链接均已通过验收。尚未连接生产服务。插件自身不应增加通用本地文件生成工具。
