# Pi Agent for Dify：首版完整功能规格

Status: ready-for-agent

本规格由已确认的访谈、实现设计及现有行为基线整理，于 2026-10-29 发布到本地 issue tracker。内核选型、首版范围、离线交付、目标架构、新会话起步、入口组织及主要验收接口均已确认；本规格是后续拆票与功能验收的依据。`ready-for-agent` 表示规格已具备实施条件，不表示功能已经实现或验收通过。

## Problem Statement

当前 CC Agent 的 Harness 主要由项目自行实现，执行循环、上下文管理、技能、工具调度、跨轮恢复及协议输出之间存在较多关联。用户希望采用专业开源社区的设计、实现和测试基础，让现有能力在 Dify 的受限运行环境中稳定、高效地工作。

目标不是持续跟随官方 Pi 更新，也不是消除全部适配与维护工作。用户需要保留当前 Dify 模型与工具接入、Skills、Tasks、工具统计、压缩、中断恢复和前端交互，避免在重构时重新维护一套执行循环，或因输出方式不同而让执行逻辑分化。

部署环境要求完全离线安装，生产使用 Linux arm64，测试使用 Linux amd64。使用者在对应环境只安装一个完整的 `.difypkg`，不能依赖额外运行服务、预装 Node 或安装时在线补齐依赖。

## Solution

构建独立的 Pi Agent Dify Agent Strategy 插件，以社区 Python `pi-agent-core-lc` 与 `pi-agent-harness-lc` 为执行内核，以已经审查的 `0.6.0` 为初始依赖基线。由 Dify 宿主提供当前会话的模型、授权工具、资源、状态及输出适配，复用社区库的正常模型与工具循环、会话构建和压缩算法。

首版以当前 CC Agent 的有效行为为验收基线。内部可分阶段构建和验证，首个可交付版本仍须完整覆盖以下范围。新插件从新会话开始，旧插件继续处理旧会话；现有前端和主要配置字段保留，只作新插件标识及状态格式等必要适配。

### 首版功能基线

| 能力 | 首版要求 |
| --- | --- |
| 输出策略 | 保留 AG-UI 与 Dify 原生入口，各自维持现有提示、技能和工具面；执行内核不依赖协议名称 |
| 模型 | 当前 Dify 会话模型；流式文本、推理、工具参数、用量、非流式回退及现有模型兼容行为 |
| 外部工具 | Dify 注入工具与远程 MCP；串行调度、权限确认、结果预算、产物展示与去重 |
| 应用技能 | 内置及应用 YAML 技能的发现、资格检查、激活、文本资源分页和跨轮恢复 |
| Tasks | 创建、更新、查询、列表、跨轮保存及模型可见的进度投影 |
| 用户交互 | AG-UI 用户提问、工具执行确认、会话授权、刷新后恢复及策略重检 |
| 会话状态 | Dify `agent_state`、容量控制、有效快照、只读摘要、修订号和持久化状态的准确表达 |
| 运行控制 | 上下文、结果、模型调用、工具调用、耗时及 token 预算；重复调用与连续错误防护 |
| 压缩恢复 | 自动与手动压缩；上下文溢出后压缩并重试一次；再次溢出明确结束 |
| 前端 | 文本、推理、工具卡片、结构化回答、附件、会话 ID、历史与中断及断流恢复 |
| 用户命令 | 当前有效的 `/help`、`/status`、`/context`、`/cost`、`/compact` 和 `/reset` |
| 交付 | 固定依赖与校验和、分架构离线包、干净环境安装启动及实际运行验证 |

## User Stories

1. 作为部署者，我希望每个环境只安装一个完整插件包，以便无需部署额外运行服务即可使用 Pi Agent。
2. 作为离线环境的部署者，我希望安装、启动和执行都不下载代码、运行时或依赖，以便在受限网络中部署。
3. 作为部署者，我希望能分别获得 Linux amd64 和 arm64 的交付物及对应验证结果，以便选择适合服务器的包。
4. 作为应用维护者，我希望首版覆盖当前全部有效能力，以便用完整业务流程评估新插件。
5. 作为应用维护者，我希望沿用现有前端和主要节点配置，以便通过选择新插件并映射参数接入。
6. 作为已有会话的用户，我希望旧会话继续由旧插件处理，以便此次重构不破坏进行中的任务和确认。
7. 作为应用维护者，我希望模型调用继续使用当前 Dify 会话的配置和授权，以便不增加另一套模型凭证。
8. 作为用户，我希望即时看到文本、推理和工具进度，以便了解助手正在处理什么。
9. 作为应用维护者，我希望不同模型的工具参数 delta、snapshot、完整单块及交错调用得到正确合并，以便不产生错参或串联调用。
10. 作为应用维护者，我希望非流式模型及已有思考兼容配置仍然可用，以便保留当前接入范围。
11. 作为用户，我希望看到可靠的模型调用、token 和工具调用统计，以便理解成本与执行过程。
12. 作为应用维护者，我希望摘要、重试、续写和最终请求都纳入运行预算，以便实际成本受统一限制。
13. 作为用户，我希望上下文接近上限时能够压缩后继续，以便长对话仍能完成任务。
14. 作为用户，我希望反复溢出或预算耗尽时明确结束并保留已完成结果，以便不会陷入无效重试。
15. 作为应用维护者，我希望助手只调用本轮 Dify 注入或配置的远程 MCP 工具，以便工具能力服从应用授权。
16. 作为应用维护者，我希望远程 MCP 的身份、headers 和连接只属于当前运行，以便不同用户之间不会共享凭证。
17. 作为用户，我希望同批工具默认串行且受到重复调用与连续错误限制，以便避免失控执行。
18. 作为用户，我希望工具失败后仍有明确结果并允许后续推理，以便历史不会因调用与结果缺失而损坏。
19. 作为用户，我希望输出过大的工具结果被安全裁剪并保留必要引用，以便后续模型请求仍可执行。
20. 作为用户，我希望 Dify 与直连 MCP 的附件和产物准确展示且不重复，以便能够访问工具产生的内容。
21. 作为上传附件的用户，我希望助手了解安全的附件元数据，以便选择合适的外部工具处理内容。
22. 作为应用维护者，我希望内置技能和应用技能按入口能力发现，以便模型只看到当前可用的指导。
23. 作为用户，我希望通过斜杠请求或模型选择激活技能，并在后续轮次继续使用，以便稳定遵循业务流程。
24. 作为应用维护者，我希望技能资源读取限定在该技能的文本资源内且可分页，以便提供参考材料而不开放通用文件访问。
25. 作为应用维护者，我希望技能失效、变更或不再符合入口资格时恢复过程能识别，以便不沿用过期指导。
26. 作为用户，我希望创建、更新和查询 Tasks，并在下一轮继续看到进度，以便处理跨轮业务任务。
27. 作为用户，我希望简单查询可以直接完成，以便不被强制创建无必要的 Task。
28. 作为 AG-UI 用户，我希望助手在缺少必要信息时提出问题，以便补充参数后继续原任务。
29. 作为用户，我希望需要确认的外部工具在获得答复前不执行，以便控制业务操作。
30. 作为用户，我希望暂停后同批剩余工具不再产生实际副作用，以便确认范围不会被后续调用绕过。
31. 作为用户，我希望刷新或插件进程重建后仍能恢复原问题与待处理操作，以便暂停不依赖进程存活。
32. 作为用户，我希望答复只匹配原问题 ID，重复或错误答复不会触发操作，以便避免误执行。
33. 作为应用维护者，我希望获准工具在恢复时重新检查当前权限、工具可用性和预算，以便确认不会绕过策略。
34. 作为用户，我希望超时且结果未知的写操作被标记为 unknown，并先查询业务结果，以便避免重复提交。
35. 作为用户，我希望选择会话授权后减少同范围的重复确认，以便在权限规则允许的范围内连续工作。
36. 作为用户，我希望会话状态随 Dify 变量恢复，且不依赖本地文件或驻留进程，以便部署重启后仍能继续。
37. 作为用户，我希望历史压缩和状态裁剪保留当前任务、技能和待处理参数，以便容量限制不会破坏恢复。
38. 作为应用维护者，我希望状态保存失败时得到明确失败结果，以便不会把一次不可恢复的执行展示为正常完成。
39. 作为前端维护者，我希望新旧插件状态格式可明确区分，并继续恢复 run、revision、状态和问题，以便保持现有会话交互。
40. 作为用户，我希望停止、断流、失败、等待及预算耗尽分别显示，以便不把连接断开误认为业务取消成功。
41. 作为 AG-UI 用户，我希望保留结构化回答、工具卡片和权限交互，以便继续使用当前前端体验。
42. 作为 Dify 原生入口的用户，我希望通过原生消息获得回答、推理和工具结果，以便使用 Dify 自带界面。
43. 作为维护者，我希望两种输出策略共享执行行为且独立渲染，以便修复工具、压缩或状态问题时不维护两套循环。
44. 作为用户，我希望帮助、状态、上下文、成本、压缩和重置命令仍然可用，以便管理当前会话。
45. 作为应用维护者，我希望错误、提示、日志和状态都不泄露配置凭证，以便安全诊断问题。
46. 作为应用维护者，我希望业务成功由工具返回的可查询证据确认，以便不会把模型陈述或 Task 完成等同于业务完成。
47. 作为维护者，我希望有真实模型回放、业务场景和分架构离线验证记录，以便判断稳定性与效率是否满足替换条件。

## Implementation Decisions

### 1. 内核归属与依赖

- 采用社区 Python Pi core/harness，初始固定版本均为 `0.6.0`；发行时固定完整传递依赖、目标 wheels 和校验和。官方 Pi 仅作设计及行为参考，不作为额外运行时。
- Pi 拥有正常模型/工具循环、会话构建及压缩算法。Dify 宿主负责产品约束和适配，不复制旧 AgentLoop，不维护另一份用于送模的权威历史。
- 所选版本未公开透传的批次结束停止及请求前检查，允许通过集中、薄的版本适配模块接入：调用基类配置构造逻辑后补接回调，保留原有准备与持久化顺序。固定版本与调用顺序必须有兼容测试。
- 私有接入点的风险已经识别；若实际接入需要复制核心循环或大范围修改社区实现，须重新评估具体设计，不能把这种改写视作普通桥接。
- 发行包独立包含所需代码和资源，不能依赖旧插件或参考源码在部署机器上存在。LangChain 的传递依赖仍按实际依赖树交付，即使模型提供方适配被绕过。

### 2. Dify 模型与同步/异步协调

- 当前 Dify 插件会话是模型与 Dify 工具调用的授权来源；普通请求、摘要、压缩、续写、最终请求和重试都经同一受控模型 Adapter。
- 保留模型流中的文本、推理、工具调用 ID/index、delta/snapshot 参数及用量转换；工具调用仅在完整校验后执行。无效参数形成明确工具错误，不把不完整 JSON 当成业务入参。
- Dify 既有历史导入在宿主侧归一为 Pi 会话输入；恢复 `agent_state` 后不得再次自动叠加相同 Dify 历史而产生重复轮次。
- 同步 Dify SDK 与 asyncio Harness 的协调必须用真实 SDK 契约验证，包括调用上下文、流式输出、超时和清理。不能仅凭将 Session 移到线程或创建事件循环就认定可用。
- 每次插件调用建立独立运行上下文，不跨用户共享模型会话、工具配置或凭证。消费者提前关闭、异常及超时都要释放本次资源；客户端停止不构成远端业务取消的证据。

### 3. 工具、权限与产物

- 工具目录整合内部认知工具、Dify 注入工具及配置的远程 MCP 普通模型工具。默认串行执行，每次真实调用前检查工具存在性、策略、确认、重复调用、连续错误及运行预算。
- 内部工具只承担技能、Tasks 和允许入口的用户提问；文件内容、代码执行、搜索和浏览通过外部工具完成。MCP 只使用受支持的远程传输，不启动本地 stdio 服务或进程。
- MCP 连接、headers 与身份限于当前运行，普通结束、暂停、异常及提前关闭均要清理。沿用现有 MCP Apps 可见性过滤规则，不增加 App 宿主。
- 保留 Dify 工具重复结果片段和语义 JSON 去重。Dify 注入工具产物沿用唯一转发路径；直连 MCP blobs 经共同宿主交付一次，普通及恢复执行行为一致。
- `files` 仅进入安全附件元数据投影，不赋予文件内容或任意本地路径读取权。
- 工具结果区分成功、明确失败、被策略阻止、尚未执行及 unknown；统计说明实际调用与未执行结果的区别，不把占位配对计为成功执行。

### 4. 应用技能、Tasks 与命令

- 维持现有内置及应用 YAML 技能的发现、资格、斜杠/模型激活、可见性和恢复行为。技能正文在需要时注入，避免同一激活被重复加入上下文。
- 技能资源只能读取归属于该技能的允许文本资源，保留路径检查、分页和长度限制。恢复技能时重新核对当前目录、入口资格及完整性。
- Tasks 的完整状态随会话保存，送模使用受控投影。Task 状态表达助手进度，业务 job/operation 引用可存于已有 metadata，不成为业务结果的替代来源。
- 保留当前六项用户命令；重置只影响当前新插件会话状态，不操作外部业务记录或旧插件会话。

### 5. 上下文与运行预算

- 请求预算覆盖实际消息、固定提示、活动技能、工具 schema、输出预留和其他实际送模内容。固定内容本身超限时明确拒绝，不能以裁剪用户请求掩盖。
- 压缩调用社区算法并更新 Pi 会话。压缩前后必须保持必要尾部工具组和消息配对；不能通过另建一套摘要历史绕过 Pi 会话。
- 发生可识别的上下文溢出时压缩并重试一次；相同恢复流程内再次溢出以 `context_overflow` 结束。普通、续写和最终请求均服从该规则；恢复不能重放已执行工具。
- 每次插件调用的模型、工具、耗时和 token 预算统一计数，摘要及重试也计入；调用内的恢复不重置预算。跨轮用户回复产生新的插件运行，保留原操作引用及上一轮统计，不把等待用户的时间视为本次执行时间。
- 结果裁剪、历史窗口、重复调用及连续错误保护保留现有有效语义。预算耗尽后停止新增真实操作，为尚未执行的 tool calls 补齐明确结果，保留完成项并输出 `budget_exhausted`。

### 6. 待处理中断与恢复

- 需要用户输入或执行确认时，保存完整问题、原调用 ID、原参数及必要恢复状态；为当前调用记录可识别的占位结果。
- 同批后续调用通过 gate 得到明确的未执行结果，不再产生真实副作用；完成本批消息配对后停止，不再请求模型。正常等待不依赖进程内 Promise 或强制 abort。
- 下一轮在导入恢复会话前校验问题/调用 ID；错误、不匹配或重复响应不能消费待处理操作。会话授权只在当前对话及允许范围有效，始终受当前策略约束。
- 获准调用必须重新检查工具可用性、当前权限、策略、预算及调用参数；不能因为已有批准直接绕过检查。可确认未执行时才进行恢复执行。
- 恢复导入前以真实工具结果或用户答案替换原占位投影，保持原 call ID 与单一对应结果。前轮未执行的尾部调用不自动重放，由后续模型重新决定。
- 超时、连接失败、进程终止或保存失败造成的外部执行结果未知，必须保留 unknown。通过业务查询、稳定操作引用或业务幂等契约核实后再决定下一步；不承诺插件单方提供跨崩溃的恰好一次执行。

### 7. 会话状态与容量

- Dify `agent_state` 是唯一跨轮权威状态，包含 Pi 有效会话分支、必要压缩记录、active leaf、Tasks、会话授权、活动技能、待处理中断和执行摘要；进程对象或本地文件不承担第二套持久化。
- 新状态采用独立版本封装 `piagent-state:v1:gzip-base64:`。Pi Agent 不导入旧 CC Agent 快照；旧前缀会话继续交由旧插件。新状态解码需限制编码及解压大小，拒绝损坏和不支持的版本。
- 输出容量沿用约 190KB 的 Dify 变量约束。上下文压缩不能当作持久化缩小；清理旧分支或压缩前原文必须保持有效投影、记录引用、leaf 和工具结果配对。
- 当前请求、必要尾部工具组和完整待确认参数优先保留。无法安全容纳时明确报告状态保存失败，不输出损坏快照或正常完成终态；原有可用状态不能被伪造的空状态覆盖。
- `state_summary` 只描述实际编码快照并保持只读。`state_ref` 区分编码成功、状态已输出及平台持久化是否已核实；插件不能仅凭输出成功宣称 Dify 变量赋值成功。
- 宿主先验证并输出状态，再允许发布终态。下一轮读回 `revision` 与 `run_id` 可用于核实实际持久化；中途断流没有可信终态时前端按未确认完成处理。

### 8. 输出策略与插件组织

- 保留 AG-UI 和 Dify 原生两个输出策略的既有产品能力。已确认在同一项目、同一个插件包中提供两个独立入口，共享执行内核。
- 入口装配能力配置与输出 Adapter。用户提问、结构化回答、技能组和提示选择属于入口能力；内核只使用能力配置，不判断协议名称。
- Pi 事件归一为少量类型化执行事件，输出 Adapter 单向消费。内核、工具与中断模块不持有协议 Writer 或 Dify 消息构造器，也不通过平台变量/blob 事件暴露平台交付细节。
- AG-UI Adapter 负责事件序列、消息/工具 ID、文本和推理开闭；Dify 原生 Adapter 负责原生消息、推理展示和工具卡片。两者直接创建各自所需的 SDK 输出，不增加第二遍中间字典分发。
- 状态和产物交付由共同 Dify 宿主承担。每次运行只选择一个输出 Adapter，不同时执行两份内核，不增加事件总线。
- 相同能力与相同输入下，仅替换输出 Adapter 不改变模型请求、工具决策、预算或快照。两个产品入口本来存在的能力差异另行验收，不要求其提示和工具面完全相同。
- 首版不要求拆成两个插件包。入口须可独立装配，为未来按发布、权限或依赖差异拆包保留空间；不预先建设独立共享库发布或多仓库同步流程。

### 9. 前端、错误与兼容

- 保留 AG-UI 原生事件与 Dify fallback 解释、工具卡片、结构化回答、附件和权限交互。新格式只增加必要的状态恢复适配，旧插件恢复行为保持可用。
- 保留会话 ID 恢复、线程映射、历史请求票据及丢弃过期结果规则，避免旧请求覆盖当前会话。SDK 绑定保持薄，不把协调逻辑移入界面外壳。
- 对外保留回答、执行元数据、`agent_state`、`state_summary`、`state_ref` 及前端需要的 `revision`、`run_id`、结束原因和问题恢复字段；字段应准确描述完成、等待、失败、预算耗尽或上下文溢出。
- 未处理策略错误输出安全的 `agent_failed` JSON 及相应失败表现，不向用户暴露 traceback。配置凭证不得进入提示、状态、日志、工具元数据或最终输出；业务正文默认不进入诊断日志。
- 保留现有主要参数：模型、上下文限制、注入工具、远程 MCP 配置、附件、指令、应用技能、用户输入、会话状态、运行配置、工具展示及思考兼容开关。新节点需显式映射，不承诺所有历史别名或零配置替换。
- Dify 兼容声明不得低于 1.7.0，实际生产目标包含 1.15.0；所声明版本应有集成证据，不能用本地 SDK 测试替代平台验证。

### 10. 离线交付与发布条件

- 分别构建 Linux amd64/arm64 的 Python 3.12 兼容插件包，包含完整运行依赖、资源、版本清单与校验和；每个环境安装对应的一个包。
- 离线指安装及运行不从公网补齐依赖、代码、资源或运行时；业务模型和工具仍经应用已配置授权的服务访问。不引入额外公共模型或遥测服务作为运行前提。
- 在干净、断网、无额外运行时的目标环境验证离线依赖解析、安装、启动及核心业务链路。某架构不能实际执行时应明确记录为待验证，不能据此宣布完整发布验收通过。
- 现有旧插件保持可用。新插件通过功能、平台、分架构和业务验收后才具备替换新业务会话的条件；内部验证切片不作为缩减首版范围的交付承诺。

## Testing Decisions

### 主要验收接口

以 Dify 策略入口作为主要测试接口：输入节点参数、当前会话与 `agent_state`，使用 fake Dify 模型/工具及可控时间，观察实际模型请求、实际工具调用、SDK 消息序列和可再次载入的状态。跨轮测试将前次输出状态直接作为下一次入口输入，并重建运行对象，证明恢复不依赖进程驻留。

多数功能通过该接口验证完整行为，避免逐层 mock 到失去真实性，也不测试内部函数名或复制实现逻辑。仅为真实易变接入点保留有限独立契约测试：Pi 固定版本的配置回调/停止顺序、模型流转换、快照 codec 与恢复、输出投影及前端恢复解释。输出 Adapter 只负责渲染的测试可以回放同一份记录事件，执行一致性须另经入口证明。

### 验收矩阵

| 编号 | 场景 | 可观察的通过条件 |
| --- | --- | --- |
| A01 | 普通回答与配置 | 两入口通过对应 SDK 输出给出回答；主要参数生效；简单查询不强制创建 Task |
| A02 | 模型流与参数 | 文本/推理、完整调用、delta、snapshot、ID/index 变化、交错调用及错误 JSON 均产生预期请求和执行参数 |
| A03 | Dify 工具与 MCP | 调用当前会话授权工具；两用户身份不交叉；远程连接在结束、等待及异常后释放；App 专用工具不可见 |
| A04 | 工具结果与附件 | 重复片段和语义 JSON 不重复展示；Dify 产物不二次转发；MCP blobs 在普通与恢复路径各只交付一次 |
| A05 | Skills | 发现、斜杠/模型激活、正文注入、分页及跨轮恢复符合当前资格；越界路径拒绝；失效技能不继续使用 |
| A06 | Tasks 与命令 | 任务 CRUD/列表跨轮一致；六项命令按契约执行；重置不修改外部业务数据 |
| A07 | 提问与确认暂停 | 问题和原参数可恢复；同批尾部工具没有真实调用；所有调用在下一模型请求前均已配对；暂停后不再请求模型 |
| A08 | 确认恢复 | 重建实例后正确 ID 可继续；错误/重复回复不执行；获准但被当前策略或预算阻止时仍不执行；原 call ID 只有一个有效结果 |
| A09 | unknown 与业务幂等 | 外部写操作超时不被当作未执行重放；通过 job/operation 引用查询状态；状态保存失败不能被当作外部回滚 |
| A10 | 请求与结果预算 | 实际系统提示、技能及工具 schema 纳入预算；过大固定内容拒绝；过大结果裁剪仍保留必要引用 |
| A11 | 溢出与运行限制 | 普通、续写及最终请求最多执行一次溢出恢复；重试/摘要共享运行预算；预算耗尽停止实际调用并补齐未执行结果 |
| A12 | 状态往返与容量 | 编码、解码、有效分支/leaf、压缩引用、任务、技能、授权及 pending 恢复一致；极限容量下不丢待处理参数 |
| A13 | 状态失败与终态 | 有效状态输出发生在终态前；编码/容量失败输出失败且无正常完成终态；不伪称平台已保存；摘要对应实际保存投影 |
| A14 | 双输出隔离 | 相同能力和 fake 输入下切换 Adapter，模型/工具调用、预算与快照有效内容一致；AG-UI 分段配对，原生卡片正确转义 |
| A15 | 前端恢复 | 新旧前缀分别正确恢复；工具卡片、结构化回答、附件、错误 prompt ID、历史及 stale-result 规则保持有效 |
| A16 | 停止与断流 | 消费者关闭可清理本轮资源；未证实的远端取消不显示成功；无终态不被视为已完成；不会串入另一会话 |
| A17 | 安全输出 | 非法配置与未处理异常产生安全错误；用哨兵凭证证明提示、状态、日志、工具元数据及最终结果均未泄露 |
| A18 | 离线与架构 | 两种目标架构依赖固定、校验和正确，干净目标环境断网安装启动并运行模型/工具/恢复链路；缺失证据明确标记 |
| A19 | Dify 集成 | 生产 1.15.0 与声明最低 1.7.0 验证变量输出、赋值及下一轮读回闭环、停止与错误行为 |
| A20 | 业务与效率 | 业务查询、技能导出、pending job、unknown 写操作及刷新确认有可查询证据；记录模型调用、token、工具统计和 p95 时延 |

### 既有测试与验证层次

- 复用现有 unittest 与 fake Dify 对象的测试习惯，以模型流、策略契约、预算、状态 codec、生命周期、Skills 和权限恢复测试作为行为先例。旧测试的内部结构不约束新 Harness 实现。
- 保留旧插件回归；受影响前端执行 Vitest、类型检查和构建。新状态支持不得移除旧格式恢复能力。
- Provider 回放使用部署版本取得的脱敏模型 chunk 样本，覆盖实际流契约；不保留凭证、用户原文或业务敏感数据。
- Dify 实际集成验证变量赋值后读回，而不以插件编码成功代替平台持久化。两个目标架构分别记录安装、启动及运行证据。
- 业务验收沿用既有场景矩阵：查询、技能指导导出、长作业 pending、unknown 写操作、刷新后确认、错误 ID、预算、断流及变量赋值失败。业务成功依据外部工具证据。
- 先记录当前基线再比较技能加载/参数有效率、恢复成功率、unknown 后重复写入、模型调用数、token 与时延，不凭空制定未经讨论的性能阈值；如未建立阈值，应交付原始对比和未决项。

## Out of Scope

- 旧 CC Agent 会话、历史状态与待处理中断迁移到 Pi Agent；旧插件继续处理它们。
- 跟随官方 Pi 每次更新、官方行为完全等价或支持 Pi 的全部 CLI/终端功能。
- Node/JavaScript Worker、额外运行服务、另一套模型凭证或另一套跨轮存储。
- MinIO、工作区、内部脚本执行、通用本地文件/代码工具、本地 stdio MCP、远程技能安装管理、显式 Memory 工具及已移除的演示命令。
- MCP Apps 宿主、新聊天平台、前端全面重写或全部历史配置别名兼容。
- 两个独立项目各自维护一份 Harness、首版多仓库/共享库发布体系，以及同一文件必须适配两种 CPU 架构。
- 在业务服务缺少幂等和查询契约时，承诺跨崩溃恰好一次执行，或把前端停止等同于远端业务取消。
- 用闭环原型代替全功能首版，或把依赖解析、单元测试通过等同于真实业务及两架构运行验收。

### 当前实施事实与未验证项

已建立本地 Python 3.12 虚拟环境并安装所选 Pi 及 Dify 相关依赖，Pi 导入已成功；已有能力配置、语义事件及输出 Adapter 的初步代码骨架。尚未形成可运行的完整插件、固定依赖发行物或安装验收记录，不能视为 A01—A20 通过。
