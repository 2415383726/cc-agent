# Harness 业务验收

CC Agent 组织模型、应用技能、任务和外部工具；业务服务持有权限、业务作业和实际执行结果。用户身份继续由应用已有节点控制。

## 应用技能的完成契约

每个重点应用技能应明确以下内容，并用小型业务场景验收：

- 触发条件与必要输入；先加载技能，工具 schema 仍全量提供。
- 操作顺序、参数含义、业务权限及需要用户回答的问题。
- 成功的可查询证据，例如导出作业 ready、业务记录版本更新、可访问的产物引用。
- 失败与 unknown 的区别；unknown 先查询业务结果，再决定是否重新提交。
- 长作业返回 job_id 后结束本轮，下一次用户请求继续查询；不无限轮询。

Task 的 status 表达助手进度。可在已有 metadata 中保存短引用，例如 `{"job_id":"export-42","evidence":{"tool_call_id":"check-42","record_version":3}}`。这些字段是引用约定，不是新存储，也不构成插件对业务成功的强制证明。业务数据和完整产物由外部工具读取。

写操作的幂等键应标识同一次业务意图，并跨网络重试保持稳定。每次新建的 plugin run_id 只用于关联诊断，不能直接充当跨轮幂等键。崩溃或状态写回失败后，应由业务服务按操作引用核实，不能只凭聊天历史重放操作。

## 最小场景矩阵

| 场景 | 验收 |
| --- | --- |
| 简单查询 | 直接回答或调用恰当查询工具，不强制创建 Task |
| 技能指导的导出 | 匹配技能先加载，参数正确，保存 job 引用，查询 ready 后交付产物 |
| 导出尚在运行 | 本轮报告 pending，Task 保持未完成，下一轮查询同一 job |
| 写操作超时 | 工具 outcome=unknown，先查询结果，避免重复提交 |
| 用户提问/确认后刷新 | 历史与 pending 一致恢复，回复绑定原 prompt ID |
| 错误 prompt ID | 不执行待处理操作，用户响应不被错误消费 |
| 总预算耗尽 | 已完成结果保留，未执行调用配对，结束原因为 budget_exhausted |
| 停止或中途断流 | 区分客户端停止与服务端结果，不显示未证实的业务取消 |
| Dify 状态赋值失败 | 不把编码成功当成平台保存成功；通过下一轮读回核实 run_id/revision |

## 分层验证

1. 仓库回归：运行 Python unittest、Vitest、TypeScript 和构建。外部模型、工具和 HTTP 使用 fake；不因此声称真实模型质量已通过。
2. Provider 回放：从部署版本取得脱敏 `LLMResultChunk` 样本，覆盖单块完整调用、delta、snapshot、id 变化、交错调用和错误 JSON；按实际契约配置流模式。不要保留凭证、用户原文或业务敏感数据。
3. Dify 集成：验证插件变量输出到赋值节点，再到下一轮输入的闭环；确认生产 1.15.0 和宣称最低 1.7.0 的行为。验证读取会话变量、停止响应、断线和取消传播。
4. 业务验收：以受控账号和样例数据，验证业务查询、作业完成、幂等重试及下载链接。需要业务服务证据，不能用插件 fake 替代。

诊断按 Dify task → plugin run_id → tool_call_id → 业务 operation/job 引用关联。关注业务成功与证据完整率、技能加载与参数有效率、unknown 后重复写入次数、刷新恢复成功率、总模型调用数、token 和 p95 时延。先记录基线，再设置阈值；日志默认保留计数、阶段、类型和安全错误码，不保留正文。
