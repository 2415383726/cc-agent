# 班子分析

将班子分析交付为可复核、可行动的业务报告：先核实单位、岗位编制和人员，再补齐必要画像和岗位要求；结论必须区分数据事实、业务研判与建议。应用 `answers-ui` 和 `answers-charts` Skill，使用少量能支撑结论的图表与卡片，不为美观堆叠组件。

## 交付目标

报告应清楚回答：分析对象和数据口径是什么；哪些岗位应配、已配、空缺或占编上岗；当前人员在职级、年龄、学历、经历和任职稳定性上呈现什么结构；哪些问题已证实、哪些待政策或人工核验；下一步做什么。

没有绩效、考核或胜任力数据时，不得写“履职表现”“能力强弱”或人员排名。家庭信息不是常规分析维度；奖励、标签和履历仅按返回事实描述，不能代替综合评价。

## 工具调用编排

工具已注册并已向 Agent 暴露。直接按下列顺序调用对应工具；不要再向用户询问工具名称、也不要因为可调用就无目的地全部调用。只使用工具说明中存在的参数和字段。

| 能力 | 何时使用 | 规则 |
|---|---|---|
| 直接调用 | 触发条件 | 调用与后续处理 |
|---|---|---|
| 工具 A（部门编码） | 用户给出单位名称、简称 | 首先调用 A 解析部门。唯一命中后立即调用 B；多条相近命中则用 UserPrompt 让用户确认。 |
| 工具 B（编制与配备） | 已确定部门编码 | 必须调用。取得编制名称、等级、岗位编码、编制数量及配备人员、正常配备/占编上岗状态，作为岗位底账。 |
| 工具 F（岗位说明书） | B 返回的每个不同岗位编码 | 对每个不同岗位编码调用 F。以“岗位编码 × 编制名称 × 等级”及编制数量建立名额；从说明书提取可核验的职责、资格和要求。 |
| 工具 C（人员画像） | B 返回的每个不同实际在岗工号 | 对每个不同工号调用 C，优先使用 `全部`。数据过大时依次取基础、学历、履历、获奖、标签，并在报告写明覆盖范围。 |
| tool search（政策检索） | 用户要求合规、政策、任职规则，或 F/C/B 暴露需政策核验问题 | 用具体关键词检索。只引用返回的文件标题、条款/原文要点；切片不足时标为待核验。 |
| 工具 D（高级检索） | 用户明确要求后备、替补或横向候选范围 | 先通过 UserPrompt 补齐目标岗位、候选范围和必要条件，再按工具字段调用 D。它不能替代当前班子名册，也不能单独证明人岗适配。 |
| 工具 E（轻量检索） | 只有姓名、别名或模糊人员线索，且 A/B/C 无法直接解析 | 仅用于定位身份或发现线索。top3 不能用于总体统计；确认工号后必须回到工具 C。 |

## 工作流

1. 提取单位、范围（整个班子/某层级/某类岗位）、关注点和数据时间口径。
2. 单位未给出时，用 `UserPrompt` 只询问单位；工具 A 返回多个部门时，用选项要求确认。编制范围无法证明是“班子”时，报告应称“当前查询范围内的编制与配备”，并提示确认范围。
3. 调用 A，再调用 B。按岗位编码、编制名称、等级和编制数量展开岗位名额，标记每个名额为正常配备、占编上岗或空缺。
4. 对 B 中每个不同岗位编码调用 F。岗位说明书是适配核验依据，不是模型自行打分的依据。
5. 对每位不同的实际配备人员调用 C。人员同时占多个编制、工号/姓名无法对应、编制数量和人员清单不一致时，保留原始事实并写入数据质量说明，不要静默去重。
6. 仅在需要政策结论时检索政策；仅在用户明确要后备或替补范围时使用 D。
7. 先计算事实底账，再写研判和建议。所有数字、人员、岗位、状态必须能回溯到工具返回。

## UserPrompt：该问就问

将 `UserPrompt` 作为分析前的正式中断，而不是在正文中猜测、罗列假设或输出模拟表单。只要缺失信息会改变分析对象、统计分母、评价标准或最终建议，就立刻提问；收到 `values` 后继续执行，不重复询问已回答内容。

### 必须中断询问

| 情况 | 交互方式 | 要问的内容 |
|---|---|---|
| 未给出单位 | 单个 `text` 字段 | 单位全称或常用名称。 |
| 工具 A 返回多个部门 | `options` 单选 | 用实际返回的部门名称/编码让用户确认分析对象；可保留自定义输入。 |
| 工具 B 的范围无法证明哪些岗位属于“班子” | `options` 或紧凑 `fields` | 分析“当前全部编制岗位”、指定岗位编码/名称，还是用户认定的班子范围。 |
| 用户要求历史时点、任期变化或“近几年”结论，却没有时间范围 | `date` 或 `daterange` | 截止日期或比较期间。不要默认把当前快照当作历史分析。 |
| 用户要求“是否合规/是否达到标准”，但没有可用政策依据或明确评价口径 | `options` / `textarea` | 选择检索的政策方向、提供适用规则，或确认仅输出客观结构事实。 |
| 工号、姓名或岗位对应关系冲突，且 A/B/C/E 无法消歧 | `options` 单选 | 展示最小必要的候选身份/岗位，要求确认后再计入统计。 |
| 用户要求提出后备或替补人选，但未给出岗位、范围或关键约束 | `fields` | 至少收集目标岗位、候选范围和必须满足的条件；然后才调用 D。 |

### 不要提问

- 单位已唯一确定、用户要的是常规综合分析：默认分析工具 B 返回的当前查询范围，不额外索要“报告格式”或泛泛偏好。
- 可由 A、B、C、F、D、E 或政策检索直接获得的信息：先查工具。
- 不影响结论的缺失字段：在数据限制中说明并跳过该指标。
- 已知问题的复述、无关个人敏感信息、模型用于排版的偏好。

### 提问设计

- 使用 `purpose: "clarification"`；问题标题要说明“为什么现在需要确认”。
- 一个阻断问题用 `options`；几个相互关联的业务条件用 `fields`，不要一次抛出大而全的问卷。
- 选项必须来自工具返回或用户已知的业务语境，不伪造部门、岗位、政策名称或人员。
- 对“班子范围”优先给出 `当前查询范围内全部岗位`、`仅领导/管理岗位（请指定）`、`指定岗位` 等清晰选项；自定义输入只在确有合理补充空间时开放。
- 对后备检索使用一个紧凑表单：`target_position`（必填）、`candidate_scope`（必填）、`must_have_conditions`（可选 textarea）、`as_of_date`（需要时）。不要用表单替代岗位说明书和政策检索。
- 表单提交只表示用户提供信息，不表示已批准任免、调整或写入任何业务数据；后续仍遵循权限和审批流程。

### 数据不足

- 不知道单位或部门有多个匹配：停止并询问，不猜选。
- 画像缺少出生日期、最高学历、任职起始时间：不生成相应指标或图表；缺失值不补造，分母使用可用样本数。
- 编制不能确认是否属于领导班子：明确范围限制，不能以“班子”名义外推。
- 岗位说明书只有文本要求、人员画像没有可对照字段：列为“待人工核验”，不生成匹配分。
- 政策检索只返回切片：不得下确定合规结论。

## 分析口径

### 编制、配备与岗位要求

必做，并清楚披露口径：

- 应配名额 = 编制数量之和；正常配备名额、占编上岗名额、空缺名额分别统计。
- 配备率 = 有实际人员的名额 / 应配名额；正常配备率 = 正常配备名额 / 应配名额。明确占编上岗是否纳入“已配备”。
- 按等级、岗位类别、编制名称或岗位编码分析缺口，只在字段真实可分组时使用。
- 对占编上岗，分别列出所占编制岗位的名称/等级/要求与实际人员已知岗位、学历、经历的差异。它是“岗位匹配需复核”信号，不能自动认定违规或不胜任。
- 岗位说明书中的任职资格、职责、能力要求，只有与工具 C 中明确事实可比对时才写“满足/不满足的已知证据”；其余写“信息不足，待核验”。

### 在岗人员结构

只基于工具 C 的真实字段，按数据可用性选择：

- 年龄：有出生日期或明确年龄才分组，例如 `35岁及以下 / 36–45岁 / 46–50岁 / 51岁及以上`，并说明数据日期。
- 学历：使用能明确识别的最高学历；不得把多段教育经历简单相加。
- 经历与稳定性：可分析本单位年限、现岗年限、管理/基层/跨领域经历，但履历必须有清晰起止时间和经历类型。
- 职级/岗位：使用实际的编制等级、岗位名称或人员基础字段，不把名称相似岗位强归同层级。
- 奖励/正式标签：仅列记录的类别、数量或覆盖情况，不折算为能力分。

不得默认使用家庭、联系方式、健康等敏感信息。除非用户有明确、合规的业务必要性和授权范围，否则不展示或推断。

### 风险研判与建议

用条件式结论，逐条写“证据 → 业务含义 → 建议”：

- 关键岗位空缺或配备率偏低：缺口风险。
- 占编上岗、重复占用、岗位等级或实际任职信息不一致：匹配风险，建议核对任职文件、岗位说明书和政策口径。
- 现岗年限显著集中在过短或过长区间：稳定性信号。
- 年龄/经验出现断层、关键岗位只有单一人选，且数据足够：梯队风险。
- 学历、经历、层级结构集中或互补：结构均衡性观察，不把“均衡”视为当然目标。

没有目标比例、岗位说明或政策依据时，用“需关注”“建议复核”，不要写“严重不足”“不符合规定”。具体任免、调整、写入和审批仍走既有权限流程。

## 最终报告结构

Markdown 是叙述层；每个 `cc-*` 卡片或图表只承担一种信息任务。按顺序输出，并省略无可靠数据支撑的模块：

1. **标题与范围（Markdown）**：单位、范围、数据来源、数据日期/未知情况；注明不替代组织任免和政策认定。
2. **执行摘要（Markdown）**：3–5 条，先写总体配备，再写最重要的结构信号和建议；每条均有事实或“待核验”边界。
3. **班子概览（`cc-record`）**：单位、分析范围、应配名额、正常配备、占编上岗、空缺、配备率、正常配备率、画像数据覆盖率。不要塞长段结论。
4. **编制配备结构（最多 1 个 `cc-chart`）**：正常配备/占编上岗/空缺等 2–12 个互斥类别且看占比时用 pie；比较岗位等级、类别或缺口排名时用横向 bar。标题/脚注标明分母和口径。
5. **岗位编制与配备明细（`cc-table`）**：岗位编码、编制名称、等级、编制数量、已配数量、配备状态、实际人员（如有）、匹配说明。稳定行 ID 使用岗位编码和名额序号；除非用户明确要求，不展示工号。
6. **人员结构（0–2 个 `cc-chart`）**：从年龄、最高学历、现岗年限/任职年限中选最有解释力的项目；每图标出 `n`、单位和分组口径。避免把同一数据在图和表中完整重复。
7. **关键岗位/成员研判（可选）**：2–4 名可比人员用 `cc-compare` 展示岗位、等级、学历、相关经历、现岗年限及可比的岗位要求证据；一个重点岗位/对象用 `cc-record`；真实任职时间顺序才使用 `cc-timeline`。
8. **风险与建议（Markdown）**：按“已确认 / 需复核 / 数据不足”标识置信度，写 2–5 条。最多附 1–2 个自然的上下文 action，例如“核验占编上岗政策口径”或“基于条件检索后备人选”；action 只触发下一轮对话，不能直接写业务数据。

### 展示选择

| 问题 | 首选 | 避免 |
|---|---|---|
| 编制状态和占比 | pie 或少量类别 bar | 雷达图 |
| 等级/岗位缺口比较 | 横向 bar | 折线图 |
| 年龄、学历、任职年限结构 | bar 或 pie | 散点图 |
| 多名成员同口径事实 | `cc-compare`；必要时小型 radar | 主观综合评分 |
| 单岗位的编制、人员和核验项 | `cc-record` | 单行表格 |
| 真实任职/调整顺序 | `cc-timeline` | Agent 执行步骤 |

雷达图只可用于 3–10 个方向一致、口径已统一的数值维度，最多比较 4 人。没有客观评分模型时，不得把学历、奖励、任职年限加权成“综合能力分”。

## 交付前检查

- [ ] 已确认部门编码、分析范围和数据限制。
- [ ] 已以工具 B 的岗位编码和编制数量统计名额，未以人员数替代岗位数。
- [ ] 已以工具 F 的岗位说明书做要求核验，未凭主观打分。
- [ ] 已对实际在岗人员取得足以支撑所用指标的工具 C 数据。
- [ ] 每个百分比有明确分母，缺失数据未混入分母。
- [ ] 图表/卡片都具有独立业务目的，没有无意义重复。
- [ ] 风险有证据与置信边界；政策结论有检索依据或标为待核验。
- [ ] 未暴露不必要个人敏感信息，未绕过权限或审批。
