# Pi Agent for Dify：设计访谈

阶段：内核选型、交付要求、功能范围、主要对外接口及完整实现设计已确认，进入实现。

## 已确认

用户选择在仓库根目录新建 `pi-agent/`，以 Pi 的架构及开源 Harness 为基础构建新的 Dify 插件。当前目标是在受限的 Dify 环境中，依靠有清晰设计、测试和社区维护的开源实现，让当前能力稳定、高效运行。用户明确不追求持续跟随官方 Pi 更新，也没有把摆脱长期维护作为主要选型目标。

1. 产品仍是 Dify Agent Strategy 插件，模型与注入工具沿用当前插件会话。
2. 新建执行实现，以复用开源 Harness 的设计、实现和测试基础为目标。以 Dify 适配、当前功能稳定性和可验证的运行行为选型；官方版本一致性和持续同步不作为首要目标。
3. 当前插件会话的模型/工具调用及协议输出由 Python 宿主持有，直接适配 Python Harness 的模型流与工具接口。
4. 已选择 `pi-agent-core-lc` + `pi-agent-harness-lc`，固定依赖并验证；已审查的 `0.6.0` 为初始基线。原 JavaScript Worker/JSONL 方案退出当前实现计划，调查文档作为历史比较证据保留。
5. Dify `agent_state` 是跨轮状态来源。每次运行从快照恢复，结束时导出新快照；进程持续存活不是正确性条件。
6. 用户已对完整实现设计回复“同意”，已授权开始实现。后续接口命名和常规内部实现由代理在已确认范围内决定。
7. 交付硬约束：使用者只能安装一个 `.difypkg`，不要求额外预装 Node、修改运行环境或部署独立运行服务。安装及运行完全离线，所有运行时和依赖均须随包提供。
8. 首个交付版本覆盖现有 CC Agent 的全部当前功能；内部可以分阶段验证，但不把闭环原型当作首个交付版本。
9. 新插件从新会话开始。原 CC Agent 的会话和待处理中断继续由原插件处理，不要求首版迁移。
10. 目标环境为生产 Linux arm64、测试 Linux amd64。建议按目标架构分别构建产物，每个环境只安装对应的一个 `.difypkg`；不假定 amd64 测试能代替 arm64 安装/运行验收。
11. 用户确认沿用现有前端、主要配置字段和 AG-UI/Dify 原生两个入口，仅作新插件标识、新状态格式等必要适配；在 Dify 中重新选择 Pi Agent 并映射参数。

## 已选内核与待验证契约

用户已确认采用 `pi-agent-core-lc` + `pi-agent-harness-lc`，在同一 Python 运行环境中适配 Dify 模型、工具、状态和输出。官方 Pi 保留为架构和行为参考。选型理由见 [ADR-0005](../../docs/adr/0005-python-pi-harness.md)。

选型已确认，但候选包的自述不等于通过 Dify 验收。已识别的溢出恢复、完整预算、持久中断和 asyncio/同步 SDK 协调，需要明确归属、实现和回归验证。稳定高效以功能契约、调用/token 成本、时延及恢复结果衡量，不因采用某种语言而直接推定。

## 已知事实与限制

- 本地参考源码中，`pi-agent-core` 和 `pi-coding-agent` 的版本为 `1.4.0`，声明 Node.js `>=22.19.0`。这不是已经选定的新插件依赖版本。
- Pi 提供官方 CLI RPC 和 Python 客户端示例，但其命令本身不等于 Dify 模型/工具回调协议。
- Pi SDK 提供自定义模型、工具和资源加载接口，并支持内存会话；接口存在不代表 Dify 集成或暂停恢复已验证。
- 现有插件使用 Python runner；部署环境是否提供兼容 Node、是否允许子进程、如何交付离线产物仍需核实或决定。
- 现有 `agent_state` 有容量上限，Pi 上下文压缩不能直接等同于持久化记录变小。快照裁剪必须保持恢复所需的工具配对、压缩记录引用和待处理操作参数。

## 事实调查

以下结论来自只读源码调查，未安装新依赖或执行 Pi–Dify 集成验证。

### Dify 宿主与交付

- 现有插件以 Python 3.12 runner 交付，目标架构为 amd64/arm64；离线构建只验证 Python wheels，尚无 Node/Pi 的构建和启动验证。见 [manifest](../../cc_agent/manifest.yaml)、[构建脚本](../../cc_agent/scripts/build_offline_package.py)。
- 排除 Pi 参考源码和依赖后，仓库没有自有 Dockerfile/Compose 证明生产环境可提供 Node。前端的 Node 依赖也不能作为插件环境的证据。
- Dify SDK Session 绑定本轮 reader/writer、session ID、身份和凭证选择上下文，不能当作长期连接配置传给 Worker；模型/工具调用由 Python 宿主保留。现有接入见 [ModelAdapter](../../cc_agent/core/model_adapter.py)、[ToolAdapter](../../cc_agent/core/tool_adapter.py)。

### Pi 模型和工具

- `createAgentSession` 支持自定义 `modelRuntime`、`customTools`、`resourceLoader`、`sessionManager` 和 `settingsManager`，工厂不直接接收 `streamFn`。可通过自定义 Provider 接入宿主模型流。见 [SDK](../../pi/packages/coding-agent/src/core/sdk.ts)、[ModelRuntime](../../pi/packages/coding-agent/src/core/model-runtime.ts)。
- 普通轮次、默认压缩（含 overflow）和分支摘要均可经过 Agent 的自定义流函数，具备统一桥接到 Dify 模型的源码依据；错误识别、认证、用量和取消仍需实测。见 [AgentSession](../../pi/packages/coding-agent/src/core/agent-session.ts)、[压缩实现](../../pi/packages/coding-agent/src/core/compaction/compaction.ts)。
- `noTools: "builtin"` 可禁用默认本地工具并保留自定义工具。自定义资源加载器并不能让默认 `/skill` 展开变为全内存：当前展开仍读取 `skill.filePath`。应用技能的接入方式尚待选择。

### 快照与中断

- `SessionManager.inMemory(cwd, options, entries)` 支持外部记录导入；应同时保存 header、entries 和 active leaf ID。导入后先恢复 leaf，再创建 AgentSession，不能只保存消息数组。见 [SessionManager](../../pi/packages/coding-agent/src/core/session-manager.ts)。
- Pi 压缩生成上下文投影，不自动删减 append-only entries，因此仍需设计 Dify 容量限制下的可恢复快照。
- 官方 RPC 的确认等待保存在进程内 Promise/Map，不能跨 Worker 重建恢复。工具阻止或异常通常成为错误结果，也不能直接当成持久暂停。见 [RPC 运行实现](../../pi/packages/coding-agent/src/modes/rpc/rpc-mode.ts)、[工具执行循环](../../pi/packages/agent/src/agent-loop.ts)。
- 中断后的批次结束、获准调用回填、策略重检、状态保存失败及 unknown 写操作处理，均属于待设计和验收的宿主契约。

## 访谈记录

### 第一轮：已回复

1. **只安装一个 `.difypkg`**。用户不接受预装 Node 的前提，希望分析最小运行环境和社区 Python Pi。原先的预装 Node 推荐不再适用。
2. **首版覆盖当前全部功能**。关键闭环是内部开发验证步骤，不构成可交付范围的缩减。
3. **新插件使用新会话**。同意旧会话继续由旧插件处理。

用户另询问“整体是否就是用 Pi 并做 Dify 桥接”；已解释执行内核复用 Pi，宿主负责模型/工具、状态和输出适配，跨轮确认仍需要专门设计。

### 首版功能基线

“全部功能”暂按现有仓库当前有效能力列出，具体对外配置及前端兼容范围待下一轮确认；已经移除的 MinIO、Memory、工作区、本地代码/文件执行及远程技能管理不随 Pi 默认能力重新引入。

- AG-UI 和 Dify 原生两个策略入口，各自的提示、技能和工具面。
- Dify 模型配置、流式文本/推理/工具参数处理、用量统计及错误处理。
- Dify 注入工具，以及按运行建立、按身份注入 headers 的远程 MCP 工具；产物展示、去重及 blob 转发。
- 应用/内置 Skills 的发现、激活、资源分页和跨轮恢复；Tasks 的创建、更新、查询和提示投影。
- AG-UI 用户提问、执行确认、会话授权与跨轮恢复；恢复后的策略重检和结果配对。
- Dify `agent_state` 的容量控制、快照版本、保存结果、`state_summary` 和 `state_ref`。
- 上下文预算、结果预算、执行预算、重复调用/连续错误防护、压缩与一次 overflow 恢复。
- 现有用户命令、附件安全元数据、结构化回答与前端会话/断流/中断恢复行为。
- 配置凭证隔离、安全错误输出和 unknown 业务结果的处理。

### 运行时交付调查：已形成候选比较

- [社区 Python Pi 候选调查](python-ports.md)：区分原生移植、不同模型栈改写和依赖 Node 的包装器。
- [单 `.difypkg` 交付调查](single-package.md)：比较官方 Pi SDK 的自包含 Worker、内置 Node 与 Python 嵌入 JavaScript 引擎。

早期调查阶段尚未选择社区移植库；当前选型以文首及 ADR-0005 为准。

用户补充“社区实现的 Pi 版本也是一个后续方案”，因此社区移植作为真实后续候选保留，不能把它视为已拒绝的路线，也不能未经选择当作官方 Pi 的等价替换。

两条路线的事实调查保留为选型证据。当前优先级以文首“当前设计建议”为准。`pi-python-core` 可作为较轻的核心及差分测试方法参考；它不包含完整应用会话与自动压缩生命周期，不等同于 core-lc/harness-lc。

内部验证顺序不改变首版交付范围。首先验证所选依赖在断网目标 daemon 中安装启动及同步 Dify SDK 的模型/工具适配，再扩大完整功能验收。生产 arm64 的验收不能用测试 amd64 代替。验证尚未执行。

### 第二轮：已回复

4. **完全离线安装**。所有运行时、Python wheels、Worker 代码和所需资源随包提供，不依赖安装时在线解析或下载。
5. **生产 arm64、测试 amd64**。当前建议分别生成对应架构的包，每个环境只安装一个；不能据此宣称用户要求同一个文件兼容两种架构。

这些选择影响运行时和依赖的体积预算，不改变首版完整功能和新会话起步的已确认范围。

本地只读体积核算：现有 `cc_agent/wheels` 按现有规则选择目标架构，amd64 为 55 个 wheels、17.49 MiB，arm64 为 54 个 wheels、16.40 MiB。现有 0.0.4 双架构离线包为 ZIP 30.45 MiB，外层 entries 未压缩合计 31.61 MiB。它们用于估计量级，不代表新 Pi Agent 的最终依赖集合或产物尺寸。

### 第三轮：选型问题已被目标澄清修订

6. 原问题以“直接继承官方修复、减少长期自行维护”为权重推荐官方路线。用户随后明确这不是主要目标，因此原推荐不再有效，也不把该问题尚未提交的选项当作已接受决策。

用户对 `pi-agent-core-lc` + `pi-agent-harness-lc` 感兴趣，要求进一步对比，尚未作出选型。补充调查见 [发布版深度比较](lc-vs-official.md)：已对应 0.6.0 发布 tag 与实际 wheel，确认该 SHA 的 Python 3.12 CI 成功；未找到 Linux arm64 Python CI 或精确官方上游版本的完整差分保证。源码中的 session、压缩、Skills、hooks 确实存在，但不自动提供一次 overflow 恢复、完整请求预算及 Dify 跨轮持久确认。LangChain 模型 adapter 可绕过，`langchain-core` 硬依赖仍需离线交付；同步 Dify SDK 与 asyncio 的协调也需验证。

因此比较的是两种维护责任：官方路线增加运行时与跨进程适配，Python 路线增加移植差异与部分 Harness 行为的补齐。两边共同承担 Dify 状态容量、中断恢复、附件和业务结果契约，不能把这些共同成本只归给某一条路线。

### 用户目标澄清

用户的主要诉求是摆脱自行拼装 Harness 的设计和实现不足，采用专业开源社区的架构、实现与测试基础；不追求持续跟随官方版本。当前的工具调用统计、Skills、压缩等能力在受限的 Dify 环境中稳定高效运行即可。这改变选型权重，但不自动证明某个社区实现已足够成熟。

据此，建议改为 Python core-lc/harness-lc 优先，将需要补齐的 Dify 运行契约明确放在适配模块中并测试。用户随后回复“同意，就选这个方案”，运行内核选型正式确认。首版全功能、完全离线、单包安装、双架构目标和新会话起步均保持为已确认约束。

### 第四轮：已回复

7. 用户回复“同意”，确认保留 AG-UI/Dify 原生两种入口、主要配置字段及现有前端，只作新插件标识和新状态格式等必要适配；Dify 中重新选择 Pi Agent 并映射节点参数。不将“全功能”自行扩大为无条件兼容全部旧配置别名。

接口核查已完成，见 [Python 运行时接入点](python-runtime-ports.md)。公开工具 hooks/串行属性与存储构造面可复用；harness 未暴露 core 的 stop/before-LLM 回调，可用薄子类覆写 `_create_loop_config` 并调用 super 后补接。该处为私有接缝，必须锁定版本并测试；尚未动态验证。

全部当前产品选择已落入 [完整实现设计](design.md)，用户回复“同意”，开始实现。后续编程中的内部接口命名和常规实现细节由代理在该范围内决定；若发现需要重写社区核心循环或改变产品契约，则带具体证据回到设计讨论。

用户指出原双协议可能侵入过深，要求重做时采用更清楚的设计。已检查旧代码的循环/压缩/中断对 Writer 的反向调用，选择少量类型化语义事件与两个独立输出 Adapter；入口能力与消息协议分开，状态及附件交付归共同宿主，先状态后终态。细节已纳入完整实现设计，继续在原授权范围内实现。
