# Pi Agent 交互可视化：可行性与第一版方案

日期：2026-10-29。

状态：设计背景文档。后续已按用户要求综合内置技能、样式、控件与本地资源形成 [规格 v1](spec.md)，实施以规格为准。尚未实现、尚未完成真实 Dify 与浏览器验收。

## 结论

可以在现有 Pi Agent + Dify + 静态 Vue 工作台上实现交互讲解。需要应用技能指导生成，以及工作台提供受限内容协议和隔离运行宿主。无需为此替换 Pi Harness、复制调度循环，或预先建立独立 Agent 后端。

优先验证“作品源码随原生回答保存”的路线。若 Dify 能完整保留回答，工作台就能从会话历史重建作品，第一版无需新增产物存储服务。当前源码支持这条路线的可能性，但端到端尚未实测，不能把它写成已经跑通。

## 已确认的体验

1. 面向交互讲解：可调参数的图解、模拟器、小工具。
2. 展示在自有 Pi Agent 工作台。
3. 滑块、播放、切换等交互留在作品内部，不发送模型请求、不调用业务工具。
4. 刷新或重新打开会话能恢复原始作品；参数回到初始值。
5. 运行时无公网资源依赖；所需资源随工作台部署。
6. 助手在交互展示有助于理解时可以主动生成，用户也可以明确请求。
7. 第一版支持内联查看与展开，不提供独立 HTML 下载。
8. 用户通过对话提出修改，新回答生成新作品，旧回答中的作品保留。

访谈记录见 [interview.md](interview.md)。本轮不扩展业务看板、表单提交、图内追问、工具授权、可视化编辑器或自托管 Pi 服务。

## ChatGPT / DeepSeek Harness 可以借鉴什么

本会话可用的 visualize 技能把生成规范与运行宿主分开：助手输出 HTML 片段，消息以路径引用内容，宿主提供展示环境。这里能确认的是本会话技能契约，不把它扩张为对所有 ChatGPT 客户端内部实现的判断。我们可借鉴生成规范与宿主分工，但应改用 Dify 可恢复的内容交付方式。

DeepSeek Harness 官方仓库固定于 `f3803c96974ad4a94195fb97e5c637e9c2a3afe3`。已确认的对应能力是 [`ui-sidebar-documentpreview`](https://github.com/deepseek-ai/deepseek-harness/blob/f3803c96974ad4a94195fb97e5c637e9c2a3afe3/packages/client/ui-sidebar-documentpreview/README.md#how-it-reads) 的交互式 HTML 文件预览：读取会话文件，通过 Blob iframe 执行，脚本沙箱不授予同源能力；直接引用的本地 JS/CSS 由宿主打包。该预览本身不注册模型工具或提示词，不能把它直接等同于一套 visualize 生成技能。

上游交付链路是 [`tool-present`](https://github.com/deepseek-ai/deepseek-harness/blob/f3803c96974ad4a94195fb97e5c637e9c2a3afe3/packages/deliverables/tool-present/README.md) 声明文件路径，记录 `deliverables/presented`，再由 [`ui-deliverables`](https://github.com/deepseek-ai/deepseek-harness/blob/f3803c96974ad4a94195fb97e5c637e9c2a3afe3/packages/client/ui-deliverables/README.md) 显示卡片并打开右侧预览。`present` 不复制作品内容；历史记录只保留声明，源文件修改或删除会改变重开结果。它的持久版本存储仍是待实现项。因此我们的历史恢复要求应建立在完整内容副本上，不能只存一个路径。此次未发现名为 `visualize` 的官方插件目录。

我们借鉴其隔离运行、完整内容检查和加载生命周期。它依赖 Host 文件读取服务，不能直接装进当前静态工作台；其交互预览也不能直接视为满足本项目的无公网资源要求。已有 [ZCode 研究](../pi-agent/zcode-genui-runtime-research.md) 是另一个参考对象，需与 DeepSeek 区分。

## 优先方案：作品是回答的一部分

建议由模型在最终回答中输出专用 fenced block，例如语言标记 `pi-visualize`。标记名与字段尚为工程建议，最终以验证后的协议为准。块内是有版本的内容描述，包含标题与自包含 HTML/CSS/JS 片段；使用标准解析器，不用正则猜测嵌套边界。

链路：

```text
用户请求 / 助手判断适合交互讲解
  → 激活应用技能
  → 模型生成普通说明 + 专用可视化内容块
  → Dify 原生 answer 保存完整内容
  → 工作台按消息身份合并完整回答
  → 完成门控 + 格式/大小检查
  → 隔离宿主显示作品
  → 历史重新加载相同源码，使用初始参数
```

这条路线不依赖 Agent 写本地 HTML 文件，也不向插件加入 shell、通用文件访问或服务端代码执行工具。本会话可用的 visualize 技能所用本地路径引用不能直接套用：我们的静态工作台无法读取插件容器内路径。

同一作品的显示身份建议由平台消息 ID、块位置、内容摘要组成；不使用“最近一条助手消息”作跨轮绑定。源码保存在平台消息中，浏览器缓存只用于加速，不作为恢复所需的唯一副本。

### 必须先修好的完整回答合并

当前事件预算是 24,000 字节，`message.end` 文本最多 16,000 字符，`last_answer` 最多 8,000 字符。它们是过程/状态投影，不能充当作品内容副本。不要通过扩大全部日志预算解决作品交付。

当前 `mergeFinalAnswer()` 对已有非空助手文本遇到不相等的平台回答时直接返回；裁剪后的过程文本可能因此挡住完整回答。历史投影在已含 `run.state`/`run.done` 时不补该条完整 answer，controller 又只合并最后一条记录。因此仅增加可视化组件会出现“当前能看，旧作品刷新后不完整”的问题。

应按每条 Dify 消息与对应 run 绑定完整原生 answer，保留推理、工具、中间消息和可信终态。不能把不同文本都拼接，也不能让历史恢复改变终态或重新执行工具。原生回答证明内容完整性，不自动证明运行成功。

### 完成与失败规则

- 流式生成中只显示生成状态，不执行半成品；闭合围栏本身不等于整条回答已确认完成。
- 停止、断线、超限或内容不完整时，不自动执行残片，不自动重发请求。
- 有完整内容但终态未知时，显示未确认状态，避免把“有文字”误当执行成功。
- 格式无效、资源不支持或运行失败时显示清楚的错误与文本兜底，不影响会话其余内容。
- 作品体积、单回答作品数量、DOM/资源预算需要有明确上限；初值以真实模型和 Dify 测试确定，不照搬桌面工具的 MB 级预算。

## 工作台运行宿主

使用独立组件组装宿主文档，提供主题、基础控件样式和受限运行环境。模型内容不得通过 `v-html` 进入工作台主 DOM。

建议 iframe 使用不授予同源能力的脚本沙箱；结合 CSP、父页面资源策略与受限消息通道。只开放尺寸/就绪/错误这类展示消息，校验实际 frame、当前消息绑定、载荷类型与体积。不给作品 Dify API key、用户身份凭据、父页面存储、工具调用或聊天发送接口。

仅写 `sandbox="allow-scripts"` 或 `connect-src 'none'` 不足以证明完全无网络出口：脚本/图片/字体加载、frame 自导航、表单、弹窗等都需一并验证与约束。iframe 也不提供可靠的恶意无限循环 CPU 隔离；需要测试异常作品的处置与恢复，不能承诺浏览器内任意代码的强资源隔离。

第一版以自包含 HTML/CSS/JS、内嵌 SVG/canvas 为内容能力。必要的图表库随构建固定版本打包，由宿主提供；不允许模型临时从 CDN 加载依赖。离线要求指可视化资源无公网依赖，模型与 Dify 服务仍需正常可达。

展开和收起应尽量保留同一 frame 实例，避免丢失当次参数；离开会话、刷新或重新加载后可回到初始值。主题、窄屏、键盘操作与减少动画偏好属于同一组件验收范围。

## 技能与输出质量

应用技能负责说明何时使用可视化、如何让首屏有意义、如何编写本地交互、如何使用宿主样式与本地资源。不能只靠系统提示“输出 HTML”。

生成目标应是一幅主要图解加少量必要控件，参数变化确实改变图形；保留可读标签、单位与文字解释。普通表格、简单事实、可静态讲清的内容不必额外生成交互作品。

修改作品走正常下一轮对话。模型历史压缩后未必还持有旧作品完整源码；涉及精确修改时，需从当前会话的原始回答定位所选作品，并将受限内容作为不可信输入提供给模型，或明确重新生成。第一版不承诺逐字保留旧源码的编辑器能力，也不将整部作品集永久塞入 Pi 状态。

## 备选交付路线

现有 `artifacts.py`、runtime artifact sink 与策略 `create_blob_message()` 有二进制附件交付接缝，可调查 Dify 原生 HTML 文件保存路线。但平台文件 URL、历史归属、身份绑定、签名过期和跨域访问均需验证；“插件已输出 blob”不能等同于“会话历史可长期恢复”。

只有回答内嵌路线在真实平台遇到不可接受的容量或历史限制时，才考虑该备选或独立产物服务。新增服务涉及部署、访问控制与保留期，届时另行评估，不作为本次已确认范围的隐含要求。

## 实施顺序与验收

1. 用固定小型作品验证 Dify 完整回答、两轮以上历史恢复与消息绑定，包含超出 16,000 字符的回答。确认应用图的 Answer 节点实际输出与保存源码。
2. 修正完整平台回答的逐消息合并；覆盖日志裁剪、日志缺失、历史分页、切换会话、停止与断线，不改变原运行终态。
3. 实现专用内容解析与同一 live/history/replay 投影；半成品或无效块不执行，普通 HTML 代码块保持原展示行为。
4. 实现隔离宿主、内联/展开、尺寸、主题和错误处置。进行网络、导航、凭据/DOM 隔离与异常内容浏览器测试。
5. 加入应用技能和固定本地资源，用真实模型验证主动生成与对话修改。

建议验收作品：一个带“到达速度/处理速度”滑块的排队模拟器。调参立即改变演示，暂停/重置正常；展开不重置；刷新和重开会话恢复原作品；再说“增加第二个处理窗口”生成新作品，旧作品仍可打开。参数与动画只是讲解模型，不宣称真实业务测算。

检查包含针对性的投影/解析测试、真实浏览器交互与隔离测试、工作台测试/构建/静态检查，以及真实 Dify 历史验收。通过本地 fake 测试不代表平台已验收。
