# 评估自建 Pi 服务后，继续以 Dify 为宿主

2026-10-29 曾据“Dify 非强制、插件扩展与技能脚本受限”决定另建 Node + `pi-durable` 的自托管多用户服务（见下方已评估设计）。同日用户判断该改造是为尚未出现的需求做重构，选择继续以 Dify 为宿主把现有 v2 插件跑通，真出现无法回避的需求时再改造。

## 考虑过的选项（已评估，暂不实施）

自托管方案已完成设计到四个关键决策：**Node 22 + `@earendil-works/pi-durable`** 作为会话运行时（提交先落盘、崩溃恢复、`watch()` 输出 value + ops、内置压缩与 inbox）；**每用户独立存储、一个用户一个 Harness**，使隔离成为结构性边界；**`bwrap` 在 `ExecutionEnv` 内做沙箱**，bash 无网络，技能脚本与 bash 同沙箱，业务数据一律由工具层带身份取数；**技能 = 目录**（`SKILL.md` + 参考资料 + 脚本 + manifest），管理端上传作为后续传输方式。前端以 durable 的 `ConversationTranscript` 重写 transcript 层，先复用 `pi_workbench` 的 Vue 壳。

放弃原因不是技术上不成立，而是成本与时机：现有 Dify 插件已实现且本地验证完整，改造要重写工具层、技能层、前端投影与部署，而当前没有用户提出 Dify 无法满足的实际需求。

## 重新考虑的触发条件

出现下列任一情况时，应重新评估而不是继续在 Dify 内加适配：

- 技能必须携带可执行脚本，且无法用外部工具表达（ADR-0001 已因此移除脚本执行）。
- AskUser 或跨轮恢复的失败开始影响业务使用，而非仅增加实现复杂度。
- 状态容量（约 190KB 对话变量）在真实会话中反复触发裁剪或保存失败。
- 新增一个工具或技能必须以重打包 `.difypkg` 并重装为唯一路径，且频率足以拖慢交付。

## 后果

`pi_dify/` 继续作为交付路径，后续工作聚焦真实平台验收：Dify 1.15.0 节点映射、真实 provider 流、真实远程 MCP、停止与历史穿透、arm64 安装与执行。未验证项见 [v2 实施证据](../evidence/v2-implementation.md)。
