# 11: 自动压缩与一次上下文溢出恢复

**What to build:** 长会话经 Pi 自动压缩后继续工作，工作台显示真实压缩活动；上下文溢出只恢复一次且不重复执行工具。

**Blocked by:** [07 状态容量、历史与会话恢复](07-state-history-recovery.md)；[10 执行预算、工具防护与用量统计](10-execution-budgets.md)

## Acceptance criteria

- [ ] 使用 Pi 会话/压缩算法，实际摘要模型调用仍走 Dify 及 10 的账本，更新有效会话记录，不另建摘要权威来源。
- [ ] 按实际系统、技能、消息、工具 schema 与输出预留判断预算；固定内容自身超限不发无益摘要。
- [ ] 正常、续写、最终请求共用一次溢出恢复额度，压缩后重试一次，再次溢出为 context_overflow；不重置预算。
- [ ] 压缩保留当前请求、必要尾部配对、active leaf 与 pending，导出/重建仍有效；存储容量与模型上下文分别处理。
- [ ] 已执行工具不在重试中重放；摘要失败/额度耗尽有准确结果，不生成虚假的压缩成功。
- [ ] 工作台展示真实压缩开始/结果和已知/估计上下文变化，不虚构百分比或将上次 usage 当当前完整预算。
- [ ] 覆盖普通和溢出路径、摘要失败、超预算、工具后压缩、含 pending 的往返；从策略到页面验证而非只调用摘要函数。

## Implementation context

- 本票依赖有效状态裁剪和统一账本，不要求先完成技能或 AskUser；用符合状态契约的技能/pending 样本检查保留行为，最终组合在 16—18 验证。
- 不强制手动压缩命令、分支摘要 UI 或旧六命令兼容。
- 当前只有少量骨架和依赖导入，前置票是否完成须检查实际验收记录。v2 是唯一范围依据，不恢复旧 AG-UI 双入口、Tasks、六命令或旧前端兼容要求。
- 每票包含自身完整行为及必要验证，优先从策略入口、真实 SDK 消息和浏览器观察；只给易变接入点补有限契约测试，不为每个内部 helper 建测试。
