# Pi Agent for Dify：实现设计

状态：以下为旧实现设计。用户在 2026-10-29 放宽前端/协议及全功能对齐要求，现应优先阅读[工作台研究与新方向](frontend-direction.md)、[规格修订说明](spec.md)及 [ADR-0007](../../docs/adr/0007-agent-workbench-scope.md)。原 AG-UI/旧前端/Tasks 硬要求不再作为首版门槛；普通 AskUser 的完成问卷加下一轮回答语义也在验证候选中。已有初步代码及依赖导入验证，尚未完成运行链路与离线交付验收。原始讨论见[访谈归档](interview.md)，内核选型见 [ADR-0005](../../docs/adr/0005-python-pi-harness.md)。

## 交付目标

在 `pi-agent/` 新建独立的 Dify Agent Strategy 插件，采用 `pi-agent-core-lc==0.6.0` 与 `pi-agent-harness-lc==0.6.0` 为初始基线，固定全部传递依赖、目标 wheels 与校验和。完全离线安装和运行；生产 Linux arm64、测试 Linux amd64，按架构分别构建，每个环境只安装一个 `.difypkg`。

首版覆盖 [现有功能基线](spec.md#首版功能基线)。新插件从新会话开始，原插件继续处理旧会话。沿用现有前端、主要配置字段和 AG-UI/Dify 原生两个入口，在 Dify 中重新选择新插件节点并映射参数。用户已确认同一项目、单个插件包提供两个独立入口，共享执行内核；按服务器架构分别构建对应包。

## 运行结构

```text
Dify AgentStrategy
  -> Python Dify 宿主：解析配置、加载本轮状态和资源
  -> Pi AgentHarness / pi-agent-core
       -> Dify 模型 Adapter：当前插件 Session、模型流转换、预算
       -> 受控工具 Adapter：内部认知工具、Dify 工具、远程 MCP
       -> 会话存储 Adapter：Pi 当前分支与应用状态
  -> 输出 Adapter：AG-UI / Dify 原生
  -> 编码 agent_state，先输出状态，再输出终态
```

Pi 继续拥有正常模型/工具轮次、消息配对、会话构建和压缩算法。宿主提供 Dify 适配和当前产品约束；不复制旧 AgentLoop，也不引入第二套模型凭证或持久化来源。旧项目中独立、适合保留的 Dify 适配实现可审查后迁入新插件；发行包不依赖仓库中另一个 `cc_agent/` 目录存在。

## 模型、预算与异步协调

- 普通请求、摘要、续写、最终请求及重试统一经过 Dify 模型 Adapter，共享本次运行预算。Dify 配置的模型仍是唯一模型入口。
- 保留现有流式文本、推理、工具参数 delta/snapshot、调用 ID/index 和用量转换规则；外部 SDK 异常转换为安全错误，不输出凭证或原始 traceback。
- 请求预算包含实际消息、固定提示和工具 schema；固定内容本身超限时直接拒绝。压缩使用社区库的算法并更新其会话记录，避免另建摘要权威来源。
- 识别上下文溢出后压缩并重试一次，第二次失败以 `context_overflow` 结束；调用内恢复不重置预算。跨轮用户回复使用新的插件运行，保留原操作引用与上一轮统计。其他工具或模型传输失败不因此自动重放业务写操作。
- 库基于 asyncio，Dify SDK 是同步调用；先验证受控异步调度与原请求上下文的协作方式。不得通过阻塞异步循环或未经验证地迁移 Session 到任意线程来假定取消/隔离已经成立。

## 双协议：语义事件与输出投影

执行内核与能力模块不持有 Writer、SDK 消息构造器或输出协议名称。Pi 原生事件由运行 Adapter 归一为输出所需的少量类型化执行事件，补充应用活动与运行结果；不复制 Pi 全部事件定义，也不把平台变量/blob/日志包装成内核事件。

每轮启动时在入口选择一个输出 Adapter，单向消费同一份事件流。AG-UI Adapter 负责其 message/tool IDs、分段开闭、AG-UI 编码及 Dify 承载；Dify 原生 Adapter 负责原生 text/JSON/log 与工具卡片。它们直接经受控消息工厂产生 SDK 消息，不再产生一套 `dify_*` 字典供策略做第二遍分发。

用户提问、结构化回答和技能组属于入口能力配置。入口在创建运行环境前选定能力，内核只使用能力接口，不查询 `agui`/`dify_native` 字符串。两种入口既有提示与工具面继续保留；切换输出适配器本身不隐式改变工具权限或运行决策。

状态变量及附件采用共同宿主交付路径，独立于两种内容输出。宿主消费运行最终结果，先完成快照容量校验并输出状态，再允许输出终态；保存失败转换为失败终态。Dify 注入工具产物维持现有唯一转发路径，直连 MCP 产物只经共同交付路径一次。

验收包括：相同能力与假模型输入下，更换输出 Adapter 不改变模型请求、工具执行、预算或快照；同一记录事件可分别投影为两种输出；中断、工具错误、断流、状态失败的语义及先状态后终态顺序一致。每个 Adapter 独立维护本轮渲染状态，不共享全局可变 Writer。

## 工具、技能与任务

- 默认沿用现有串行执行语义；每个宿主工具标记 sequential，执行前检查策略、重复调用、连续错误和总预算，执行后施加结果预算与产物转换。
- 内部工具继续提供 Skills、技能受限文本资源、Tasks 以及 AG-UI 的用户提问。文件、执行、搜索和浏览由 Dify 工具或配置的远程 MCP 提供。
- 远程 MCP headers、连接和身份限于当前运行；结束、异常、中断及提前关闭均释放连接。保留 Dify 产物单一路径、语义去重和直连 MCP blobs 转发。
- 应用/内置技能由宿主提供受控资源，维持当前技能资格、激活、分页和恢复行为。保留任务的完整状态及送模投影。

## 用户提问和确认后的跨轮恢复

1. 工具需要用户输入时，保存完整待处理调用或问题，返回有标记的占位结果。
2. 同批后续工具经 gate 得到明确的未执行结果，真实工具不再执行；由 core 完成全部 tool-call/result 配对。
3. 批次末停止继续调用模型，保存状态并结束本次插件调用。正常等待不用进程内 Promise 或 `abort()` 模拟。
4. 下一轮核对 prompt/tool-call ID；用户答复只匹配对应问题。获准调用仍检查本轮工具是否存在、策略、预算和当前权限，再执行一次。
5. 在恢复导入前，用真实执行结果或用户答案替换该待处理结果的快照投影，维持单一结果与原 tool-call ID；未执行尾部调用由后续模型重新决定。
6. 外部执行结果未知时保留 unknown，禁止当作未执行直接重放。状态写回失败也不等于外部操作回滚。

## 版本适配层

0.6.0 的 AgentHarness 没有透传 core 已有的 `should_stop_after_turn` 和 `before_llm_call`。计划使用一个薄子类覆写 `_create_loop_config`：先调用 `super()`，再补接所需回调，保留其现有准备、持久化和 hook 顺序，不复制 loop 或整段私有方法。

此处依赖一处私有接缝，须对固定版本/hash、factory 签名、回调顺序、中断后无模型请求、所有结果配对和预算耗尽建立契约测试。快照导入使用公开 SessionStorage/Session 接口。依据与限制见 [接口核查](python-runtime-ports.md)。若实际实现需要大范围改写核心循环，重新提交具体设计，不把它藏在适配层中。

## 跨轮状态与前端

- `agent_state` 是唯一跨轮权威状态，包含 Pi 当前有效分支、必要压缩信息、active leaf、Tasks、授权、技能与待处理中断，以及执行摘要。
- 采用独立版本封装 `piagent-state:v1:gzip-base64:`；不读取旧 CC Agent 会话。保留前端所需的 revision、run_id、运行状态和问题恢复视图字段，为现有解码器增加明确的新格式支持。
- 序列化约束继续按约 190KB 处理；压缩上下文不等于存储记录已缩小。清理无关旧分支或压缩前原文时，须保持当前投影、引用、leaf 与工具配对一致，以导出/恢复往返测试证明。
- 当前请求、必要尾部工具组、待确认参数优先保留；无法安全装入时明确返回保存失败，不输出正常完成终态或损坏状态。
- `state_summary` 保持只读；`state_ref` 区分编码/输出成功与平台实际持久化未知。前端继续区分完成、失败、等待、预算耗尽及无可信终态的断流。

## 验收与实施顺序

内部按依赖、模型/工具、会话/预算、中断、技能/任务、双协议/前端、离线包推进；首个可交付版本仍按完整功能验收。

1. 锁定依赖并校验 Python 3.12 两架构全部 wheels 离线解析；检查新包 API，执行上游相关测试及版本适配契约测试。
2. 用 fake Dify Session 回放流式工具参数、产物、压缩、预算、错误和跨轮恢复；验证重复调用、不匹配回复、unknown 与保存失败等关键场景。
3. 沿用并迁移 [业务验收矩阵](../../docs/harness-validation.md)，运行新插件测试、受影响前端测试、类型检查和构建，保留旧项目回归。
4. 在断网且没有额外运行时的干净 Dify 环境安装并验收。amd64 与 arm64 分别验证；若无可用 arm64 执行环境，交付中明确标为待生产侧验证，不能用依赖解析替代运行结论。
5. 对真实业务场景检查工具统计、技能有效性、恢复结果、模型调用数、token 与时延。单元测试通过不等于真实业务成功或效率已达标。

实现中常规内部接口和命名由代理在此范围内决定。需要改变产品契约、引入额外服务或重写社区核心时，先带具体证据回到设计讨论。
