**What to build:** AG-UI 用户收到助手主动提出的问题，刷新后回答即可继续任务，并获得现有结构化回答；Dify 原生入口维持其自己的提示和工具面。

## Acceptance criteria

- [ ] 用户提问工具只在允许的入口能力下可见；内核不根据 agui/dify_native 字符串决定能否提问。
- [ ] 提问产生 awaiting_user 和可恢复问题，当前批次后续真实工具受 gate 阻止，下一模型请求在回复前不会发生。
- [ ] 刷新/重建后正确回复替换原占位结果并继续推理；错误/重复问题 ID 不消费答复或执行关联业务操作。
- [ ] AG-UI RUN_FINISHED 中断表现及现有前端问题卡片、选项/自由输入和恢复路径符合当前契约。
- [ ] 通过结构化回答技能完成现有回答展示，保留其引用、卡片和附件适配；不重写整个前端或把技能逻辑放进输出 Adapter。
- [ ] Dify 原生入口维持现有普通回答与技能范围，不因 AG-UI 能力新增而暴露其专用认知工具。
- [ ] 相同能力条件下回放两个输出 Adapter 的执行决策一致；入口本来不同的能力分别测试。

## Implementation context

- 按已确认规格实施：社区 Python Pi core/harness 0.6.0 为初始基线，单项目单插件双入口；Dify 持有模型/工具授权与唯一跨轮状态。内部只提供认知工具，不恢复已移除能力。
- 本票依赖技能目录/资格与通用持久暂停，避免再实现一套 UserPrompt 状态机。
- 后续 /reset 应能清理该待处理中断，整体命令验收在 14 与最终集成中确认。

## Verification

从 AG-UI 入口触发真实提问—保存—刷新—回复—结构化回答；再验证原生入口工具面与错误/重复回复，不仅断言输出事件存在。

通过 Dify 策略入口及真实应用输入/输出验证行为；采用现有 unittest/fake Dify 和前端回归的惯例。仅对真实变化接入点补充有限独立契约测试，不断言内部实现结构。不得因上游票已有骨架或 fake 通过，就省略本票端到端行为验收。
