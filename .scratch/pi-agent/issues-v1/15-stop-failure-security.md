## Acceptance criteria

- [ ] 分别在模型流、Dify 工具、MCP 工具及确认恢复阶段提前关闭消费者或触发超时，释放本轮异步任务和连接，不串入另一会话。
- [ ] 区分客户端停止、传输中断、明确取消及远端结果未知；没有业务证据时不显示远端取消成功。
- [ ] 有可信终态时准确区分失败、等待、预算耗尽、context_overflow 和完成；没有终态时前端保留未确认状态。
- [ ] 未处理策略错误产生安全 agent_failed JSON 和对应输出；普通工具错误仍有配对结果，不能把原始 traceback 发给用户。
- [ ] 状态编码/输出失败不产生正常完成终态；不因最终日志或渲染异常再次执行已经完成的工具。
- [ ] 以哨兵凭证覆盖配置、模型/工具 SDK 异常、MCP headers、日志、状态、元数据和最终输出，证明无凭证泄露。
- [ ] 安全错误与清理通过入口行为验证，保留现有前端 native/fallback、stale-result 和附件回归。
- [ ] 必要的失败信息保留安全错误码、阶段与 run/tool 引用；默认诊断不保留业务正文。

## Implementation context

- 按已确认规格实施：社区 Python Pi core/harness 0.6.0 为初始基线，单项目单插件双入口；Dify 持有模型/工具授权与唯一跨轮状态。内部只提供认知工具，不恢复已移除能力。
- 各功能票在引入行为时就要处理错误和清理；本票验证复杂关闭/恢复组合及跨入口安全收尾，不是把之前的错误处理推迟到最后。
- 真正 Dify 停止/取消传播与真实平台变量赋值仍需 16、17 的平台验证，fake close 不等价于平台实测。
