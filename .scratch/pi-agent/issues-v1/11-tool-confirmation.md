## Acceptance criteria

- [ ] 需要确认时记录完整问题、原调用 ID/参数和待处理中断；原调用产生可识别占位，同批尾部工具不实际执行且全部配对。
- [ ] 工具批次完成后不再发起模型请求，输出 awaiting_user、有效恢复状态及前端确认交互；正常等待不依赖驻留 Promise 或强制 abort。
- [ ] 通过状态重建运行后核对 prompt/tool-call ID，错误、重复或不匹配答复不消费原问题，也不执行外部工具。
- [ ] 批准恢复前重新检查当前工具存在性、参数、策略、权限、预算及保护限制；拒绝或新策略阻止时有明确结果。
- [ ] 可确认未执行时才实际执行一次，并在导入 Pi 会话前替换原占位，保持原 call ID 与唯一有效结果；尾部未执行操作不自动重放。
- [ ] 会话授权在当前对话及允许范围生效；后续授权不能绕过调度策略，另一对话不继承授权。
- [ ] 现有前端刷新后从新状态恢复确认问题，原生入口保留其既有确认表现；输出差异不改变恢复决策。
- [ ] 测试暂停后的模型零新增请求、尾部工具零调用、拒绝/批准/错误 ID/重复答复，以及批准后工具移除或预算变化。

## Implementation context

- 按已确认规格实施：社区 Python Pi core/harness 0.6.0 为初始基线，单项目单插件双入口；Dify 持有模型/工具授权与唯一跨轮状态。内部只提供认知工具，不恢复已移除能力。
- 本票使用 Dify 外部工具完成确认全链路；MCP 确认及恢复后的 blob 在 13 集成，主动用户提问在 12 复用这一持久暂停能力。
- 超时未知不能直接重放；本票不得承诺跨崩溃恰好一次执行。
