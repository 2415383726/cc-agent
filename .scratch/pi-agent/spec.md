# Pi Agent for Dify：Agent 工作台规格 v2

Status: ready-for-agent

版本：2；发布日期：2026-10-29。本文为当前实施依据，取代 v1 的全量旧功能、固定 AG-UI 双入口及旧前端兼容要求。规格发布不代表实现或平台验收已经完成。

## Problem Statement

用户希望采用专业开源社区的 Harness 设计与实现，改善自行编写 CC Agent 时在执行循环、技能、上下文、工具调度和恢复方面的不足。在受限 Dify 环境中，让模型、工具、Skills、压缩和工具统计稳定高效地工作，比持续跟随官方 Pi 更新或复刻编程终端更重要。

用户需要能看见 Agent 工作的 Web 界面：助手正在处理什么、调用哪些工具、使用哪些技能、得到什么结果，以及需要用户回答什么问题。旧问答布局、定制卡片、AG-UI/CopilotKit 和独立 Tasks 系统均不是必须保留的约束，不应为了对齐旧实现重新造一套 Harness 或工作台。

插件必须使用当前 Dify 会话的模型与授权工具，通过 Dify 对话变量恢复状态。生产使用 Linux arm64，测试使用 Linux amd64；每个环境只安装一个完全离线的插件包，不能额外部署 Pi 后台、预装 Node 或在线补齐运行依赖。

## Solution

新建独立的 Pi Agent Dify Agent Strategy 插件，采用社区 Python pi-agent-core-lc 与 pi-agent-harness-lc，初始版本均固定为 0.6.0。Pi 负责正常执行循环、会话构建和压缩；Dify 宿主负责模型、授权工具、技能资源、预算、跨轮恢复和平台输出，不复制旧 AgentLoop。

前端优先抽取 **Leyline 的 Vue 3 聊天组件**，复用工具活动、技能轨迹、思考、消息、结果和输入交互，替换其原后台控制层；参考社区 Pi Web 的问卷交互补齐 AskUser。交付静态 Web 构建物，不使用 Leyline 的 Node/Pi 常驻后台、桌面运行时或本地工作区能力。

输出采用有限的 Pi 风格消息/工具生命周期，加上 Dify 宿主的活动、提问、状态和终态，经 Dify 请求及 SSE 承载。前端 Dify 控制层负责发送、历史、会话定位、附件、停止和答复，不只是替换流地址，也不宣称兼容全部官方 Pi RPC。

### 首版交付边界

| 能力 | 首版要求 |
| --- | --- |
| Harness | 实际复用社区 Pi 的执行、会话和压缩能力，保持薄的 Dify 适配边界 |
| 模型与工具 | 当前 Dify 模型、注入工具、授权远程 MCP；流转换、预算、统计及可靠结果交付 |
| 应用技能 | 发现、资格检查、用户/模型激活、受限文本资源读取及跨轮恢复 |
| Agent 工作台 | Vue 聊天核心复用；回答、真实思考、工具、技能、压缩活动、产物及运行状态 |
| AskUser | 可恢复问卷、下一轮答复、重复/过期校验和确定性暂停；与工具审批分开 |
| 会话控制 | Dify 权威状态、容量控制、自动压缩、一次溢出恢复、停止与安全失败 |
| 离线交付 | Python 3.12；amd64/arm64 分别构建及运行验收，每环境安装一个完整插件包 |
| 不作前提 | AG-UI、两个输出入口、旧卡片/结构化答案格式、Tasks 系统、完整 Pi Web 后台 |

## User Stories

1. 作为插件维护者，我希望复用 Pi Harness 的执行与会话能力，以便以社区实践改善自研 Harness。
2. 作为应用维护者，我希望新插件独立存在，以便旧 CC Agent 继续服务旧会话。
3. 作为应用维护者，我希望只使用当前 Dify 配置的模型，以便沿用已有凭证和模型治理。
4. 作为应用维护者，我希望摘要、压缩和重试也经过 Dify，以便不出现额外模型来源或遗漏计费。
5. 作为用户，我希望在 Vue Web 工作台中看到助手工作过程，以便理解当前进展。
6. 作为用户，我希望流式和最终回答合并一致，以便不会看到两份相同答案。
7. 作为用户，我希望只看到模型实际提供的思考，以便界面不虚构推理过程。
8. 作为用户，我希望看到工具开始、参数、可用更新和结束结果，以便知道助手做过什么。
9. 作为用户，我希望通用工具也能展示结果或错误，以便没有定制卡片时仍可使用。
10. 作为用户，我希望看到技能的真实激活与资料读取，以便知道助手依据什么业务指导。
11. 作为用户，我希望工具、技能、压缩与答案层次清楚，以便界面体现 Agent 协作。
12. 作为用户，我希望能展开和折叠执行详情，以便快速阅读或核对操作。
13. 作为用户，我希望上传附件并查看真实工具产物，以便完成业务任务。
14. 作为用户，我希望同一执行和产物只出现一次，以便不会误认为发生重复操作。
15. 作为应用维护者，我希望工具继承本次 Dify 身份，以便用户间不串用权限。
16. 作为应用维护者，我希望 MCP 连接和身份限于当前运行，以便授权生命周期清楚。
17. 作为应用维护者，我希望不内置任意 shell 或文件操作，以便外部能力由授权服务提供。
18. 作为应用维护者，我希望按应用配置筛选技能，以便只使用当前有效的业务指导。
19. 作为用户，我希望主动请求或由模型选择激活技能，以便专业流程自然参与任务。
20. 作为应用维护者，我希望技能资源受范围和分页限制，以便不能越界读取。
21. 作为用户，我希望下一轮按当前资格恢复技能，以便连续工作不丢失有效上下文。
22. 作为用户，我希望通过单选、多选或文本问卷回答助手，以便方便补充信息。
23. 作为用户，我希望提问后助手确实等待，以便不会在收到答案前继续执行。
24. 作为用户，我希望刷新后仍能看到待答问题，以便不依赖原浏览器或插件进程。
25. 作为用户，我希望答复后继续同一任务并保留历史答案，以便理解决策来由。
26. 作为用户，我希望错误、重复和过期答复不会触发重复工作，以便误操作可控。
27. 作为用户，我希望普通提问和工具审批展示不同，以便清楚是在提供信息还是授权操作。
28. 作为应用维护者，我希望批准后仍检查当前权限与策略，以便旧授权不绕过限制。
29. 作为用户，我希望下一轮恢复历史、技能和待处理事项，以便继续已经开展的工作。
30. 作为用户，我希望状态损坏、过大或保存失败有准确说明，以便不把未保存工作当作可靠完成。
31. 作为用户，我希望切换对话与加载历史不混入其他会话，以便工作台可信。
32. 作为用户，我希望断流或刷新不会自动重发业务请求，以便避免重复写操作。
33. 作为应用维护者，我希望限制模型、工具、时间和 token，以便控制成本与失控调用。
34. 作为应用维护者，我希望查看实际调用、用量、错误和耗时，以便评估稳定性与效率。
35. 作为用户，我希望长对话自动压缩后继续，以便在有限上下文中完成任务。
36. 作为用户，我希望上下文溢出受控恢复一次，以便不无限重试或重放工具。
37. 作为用户，我希望完成、等待、失败和停止准确区分，以便理解当前状态。
38. 作为用户，我希望外部结果未知时被明确告知，以便先查询业务结果再决定是否重试。
39. 作为应用维护者，我希望错误不泄露凭证或 traceback，以便安全定位故障。
40. 作为部署者，我希望在 amd64 测试环境离线安装一个包，以便无需现场补依赖。
41. 作为部署者，我希望在 arm64 生产目标环境独立验证，以便有真实生产架构证据。
42. 作为部署者，我希望工作台可静态托管，以便不增加常驻 Agent 后台。
43. 作为维护者，我希望内核与复用前端的版本、来源和许可可追溯，以便长期维护。
44. 作为维护者，我希望主要通过 Dify 入口与浏览器验证，以便覆盖真实接入行为。
45. 作为用户，我希望首版聚焦工具、技能、提问与过程展示，以便不被价值较低的完整工作台功能拖延。

## Implementation Decisions

### 1. Pi 内核与 Dify 宿主

- Pi 持有正常模型—工具循环、有效会话投影和压缩算法。宿主提供本次请求配置、模型流、工具、技能、状态和输出适配；不复制旧循环，不在浏览器执行 Agent，不维护第二套权威历史。
- 两个 Python Pi 包固定 0.6.0 起始基线，锁定完整依赖及校验和；LangChain 等实际传递依赖一并离线交付，不能因自定义模型流就假定可直接删除。
- 普通、续写、摘要、压缩和最终模型请求共享 Dify 模型入口与运行预算。公共策略 hook 与展示订阅分开，工具权限不依赖前端消费。
- Harness 未透传的 core 请求前/停止回调，允许用一个最小版本适配子类补接：保留上游配置工厂，再接入必要回调。固定私有接缝的签名、顺序和停止契约，不复制循环或全局 monkeypatch。
- 同步 Dify SDK 与 asyncio 协调须经真实 SDK 上下文验证，不假定 Session 可任意迁移线程；不同运行不得共享请求身份、连接和渲染状态。

### 2. Vue 社区聊天核心

- 首选 Apache-2.0 的 Leyline，固定来源提交 a368c8b7590b88bb138c024b7dd8414b3dcc2a73。复用转录/流式消息、工具及技能卡、输入区和必要 Markdown、主题、滚动模块，以已有 props/emits 为接缝。
- 从原应用抽出聊天组装，替换 REST/WS 会话控制；不整体搬入原外壳、Pi SDK 后台、项目/机器、终端、Git、Electron 或 tracing 服务。
- 解耦浏览器构建对 Pi SDK 包内高亮资源的直接路径依赖，使用独立锁定资产；静态页面不加载 Agent SDK，不依赖公网字体、脚本或 CDN。
- 首道实施验收是无原后台的静态构建与事件回放，覆盖工具、技能、问卷和终态。源码存在不是抽取成功；发现超出这些边界的硬耦合时，提供可重现证据再调整，不能静默扩成完整工作台重写。
- jmfederico/pi-web 作为问卷交互/按轮语义参考和备用候选，不同时维护第二套前端。实际复用保留许可、版权、必要 NOTICE、来源提交与修改说明；不用 stars 代替验收。
- 构建期允许 Node。前端部署到现有 Web 静态托管位置，不增加运行期 Node/Agent 服务；“一个 difypkg”针对 Dify 插件安装，不宣称插件自动托管任意前端。

### 3. 浏览器控制层与产品入口

- 首版交付一个 Agent 工作台入口，不强制同时交付 AG-UI/Dify 原生两个独立策略。执行与输出继续隔离，未来其他入口不应改写执行流程。
- Dify 控制层负责发送、会话 ID 恢复、历史及实时合并、上传/产物、停止和问卷/审批答复；聊天组件只消费展示状态并发出用户动作。
- 应用节点显式声明并映射 query、model、tools、files、instruction、技能、MCP、运行配置、agent_state 和结构化交互入参；不能假定任意 Web inputs 自动传给插件。
- 保持对话映射、历史请求票据及过期结果规则。每个对话默认只允许本客户端发起一个活动请求，但这不等于多客户端并发锁。
- 必须有新对话、发送、停止、历史恢复、附件及问卷/审批；只展示真实支持的控制项，不保留失效的 steering、分支、队列、模型设置或文件操作按钮。
- Dify 原生最终文本仍供平台回答/历史使用，工作台合并同一答案，不重复展示。无需保留旧结构化答案 schema 或旧卡片语义。

### 4. 显示事件与 Dify 传输

- 采用少量类型化消息开始/增量/结束、工具开始/更新/结束，以及宿主技能、压缩、提问和运行事件；不复制全部官方 RPC，不增加通用事件总线。
- 显示契约包含 schema 版本、run ID、本轮顺序及消息/内容块/tool-call ID。Python Pi 与官方 TS 的字段及 settled 语义明确映射，不能任意 model_dump 后声称 RPC 兼容。
- 过程通过插件 LOG 的 JSON data 承载，前端解开真实 Dify 应用 SSE 的 Agent 日志包装；最终文本、变量和 blob 使用各自 SDK 消息。部署实例的穿透行为必须实测。
- delta 累加到所属内容块，最终消息覆盖临时消息；工具 end 与 tool result 合并为同次执行，重复事件不生成第二张卡或产物。
- 保留起止和最终内容，合并过密更新，限制事件数、单项大小及历史日志体积。日志 ID/更新策略须证明实时和历史可重建，不能逐 token 无界保存全量快照。
- 仅输出允许展示字段，不转储 provider 请求、headers、内部事件对象或整个会话。未知工具有通用兜底；坏事件和不支持版本安全拒绝或提示。
- Pi settled/message end 不是宿主终态。有效状态输出后宿主才发布终态，也不等于平台已持久化或所有业务成功。
- 顺序号用于关联去重，不提供任意断线重放。恢复最近历史/提交投影，无可信终态则显示未确认，禁止自动重发业务请求。

### 5. 模型、预算与压缩

- 支持当前 Dify 文本、实际推理、完整工具调用、参数 delta/snapshot、交错调用、ID/index、用量和必要非流式回退。参数模式显式配置，不猜 JSON 前缀。
- 只执行结束后校验有效的完整参数；坏 JSON、缺失工具及流失败产生配对结果，不执行半截参数。
- 请求预算包含实际系统指令、技能、消息、工具 schema 和输出预留。固定内容超限直接拒绝，不做无益摘要；估计值与 provider 已报告用量分开标明。
- 本次调用所有模型请求统一计数，包含摘要、重试、续写及最终请求；工具次数为实际执行。下一轮为新运行预算，保留前轮统计及操作引用。
- 自动压缩使用 Pi 会话/压缩机制，保留当前请求、必要尾部工具组和 pending；界面仅展示真实压缩事实，不伪造百分比。
- 正常、续写、最终请求共用一次溢出恢复额度：压缩后重试一次，再溢出以 context_overflow 结束；不重置预算或重放已完成工具。
- 限制模型/工具次数、耗时、已报告 token、重复调用、连续错误和结果大小。耗时及停止为协作式，不保证强行撤销同步 SDK 或已发出的业务操作。

### 6. 外部工具与应用技能

- 以受控 AgentTool 适配 Dify 注入工具和远程 MCP，默认串行；真实执行前检查当前可见性、策略、授权、预算和重复/错误防护。
- 不启用 Pi 编程工具的 bash/read/write/edit 工厂，不提供通用本地 I/O 或 stdio MCP。文件、执行、检索和浏览由 Dify 或授权服务提供；技能读取仅限所属技能的受控文本资源。
- MCP 身份、headers、连接限于当前运行，结束、等待、异常和提前关闭均释放；App 专用工具不作为普通模型工具注册，恢复时获取当前身份和工具。
- 保留 Dify 重复半段及语义 JSON 去重，不增加 Dify 工具产物第二转发路径；直连 MCP blobs 在普通与审批恢复路径均只经共同交付点一次。
- files 仅提供安全元数据，不等于已读内容；需要时由授权外部工具读取。通用卡展示未知工具，展示预算与送模结果预算分开。
- 技能支持内置/应用发现、资格检查、用户/模型激活、正文注入、分页和恢复；拒绝越界及失效资源，下一轮复核资格。
- 使用 Pi 资源/hook/消息机制，不另建技能循环。界面映射真实激活和读取，不能靠伪造 SKILL.md 路径、工具名或百分比制造技能进度。
- 首版不内置独立 Tasks 工具、持久任务模型或面板；工具/技能活动及实际业务 operation/job 短引用承担过程展示，普通问答不强制建任务。

### 7. AskUser 与工具审批

- 普通 AskUser 采用“完成提问工具、下一轮接收答案”：结果包含稳定问题 ID、题目/选项、回答类型及校验约束，支持单选、多选、文本与一份问卷多题。
- 提问工具返回完整可持久化问卷，同时形成当前 pending。原结果表示问题已提出，不持有进程内 Promise，也不在恢复时把旧提问结果替换为答案。
- 提问后确定性 gate 阻止同批尾部真实工具，补齐未执行结果；批次末阻止下一模型请求。不能只依赖 terminate 或“独占最后一个工具”的提示。
- 输出有效状态后以 awaiting_user 结束。问卷卡需可操作表单与历史结果，不把 JSON 文本或原项目 extension confirm 当作完整 AskUser。
- 下一次 Dify 请求显式携带交互类型、问题 ID 和答案。校验当前权威 pending、选项及消费记录后，将答案作为新用户消息加入 Pi，再清除对应 pending 并继续。
- 缺失、错误、过期、重复答案不得执行工具或继续模型，返回可理解的拒绝/当前等待投影。取消为明确动作，不将普通聊天文字意外当作答案或批准。
- 工具审批为独立 pending 和界面，保存操作 ID、完整参数及授权范围；普通问卷不能授权，拒绝不执行，会话授权不绕过策略和服务端权限。
- 审批恢复仅在确认原操作未执行时，按本轮身份重检工具、策略、许可与预算再执行。必要会话投影在导入前形成单一有效结果，不调用不存在的替换 API；原批次尾部不自动重放。
- 外部超时、断连、进程终止或保存失败引起的结果未知保留 unknown 与业务引用；先查询或按明确幂等契约核实，不按未执行重试，不承诺跨崩溃恰好一次。
- Dify 原生 Human Input 非前置，AgentStrategy 发消息不能直接获得原生工作流暂停；首版用下一轮聊天闭环，不引入额外网关。

### 8. 权威状态、恢复与终态

- agent_state 是唯一跨轮权威，包含 Pi 有效会话、必要压缩记录和 active leaf、活动技能、会话授权、pending、必要消费记录及统计；本地文件、浏览器缓存和驻留对象不是另一存储源。
- 使用独立 piagent-state:v1:gzip-base64: 封装，限制编码和解压大小，拒绝损坏/未知版本；不读取 CC Agent 旧快照。
- 沿用约 190KB 编码边界并验证实际限制。上下文变短不等于存储缩小，裁剪须保留有效引用、leaf 和工具配对。
- 当前请求、必要尾部工具、完整问卷/待确认参数优先；无法安全保存则 state_save_failed，不用空快照覆盖旧状态，不发布正常完成终态。
- state_summary 只描述实际编码快照。state_ref 提供会话定位、revision、run ID 和交付状态，区分编码、输出与平台持久化未知；SDK 输出不是变量赋值证据。
- 先验证和输出状态，再发布完成、等待、预算结束或失败。下一轮读回 revision/run ID 核实状态；revision 不提供原子并发控制。
- 浏览器从 Dify 可恢复历史/展示投影重建问题与活动，服务端始终按当前 agent_state 校验。缓存仅存草稿，没有可验证状态不凭缓存继续审批。
- 下一模型请求前所有 assistant tool calls 都有对应结果，包括失败、预算、暂停和跳过；恢复不重放已完成工具，不伪造成功。
- 客户端停止尽力通知 Dify；宿主实际感知后清理并尽可能保存准确结果。断开不等于业务撤销，无可信终态显示未确认且不自动重发。

### 9. 安全、配置与离线交付

- 保留模型、query、工具、指令、上下文、文件、技能、MCP 及运行配置的必要能力，并给出新节点显式映射；无需全部历史别名、旧命令或零配置替换。
- 未处理错误为安全 agent_failed JSON，带安全代码、阶段和 run ID，不暴露原始异常/traceback。配置 secrets 不进入提示、状态、日志、工具元数据或最终输出。
- 分别构建 Linux amd64/arm64 的 Python 3.12 完整 difypkg，包含运行依赖、资源、许可、版本清单与校验和，不依赖预装 Node、额外 Agent 服务或安装时下载。
- 完全离线指安装/运行不从公网补齐代码、依赖、资产或运行时；业务模型/工具仍访问应用授权服务。静态前端不依赖公网资源或公共遥测。
- Dify 兼容声明不低于现有 1.7.0，生产目标包含 1.15.0；声明版本的关键传输、状态、交互须有平台证据，不暗中提高基础要求。
- 新插件独立身份、新会话；旧插件及旧前端继续独立可用，不在此次裁剪其协议、Tasks 或状态。

## Testing Decisions

### 主要验收接口

沿用用户已确认的 **Dify 策略入口与跨轮状态恢复**，再从浏览器动作验证工作台闭环。输入实际节点参数、可控模型/工具，观察真实请求、执行、SDK 消息、页面结果及可再次载入状态；跨轮重建运行对象并包含浏览器刷新，不依赖原进程驻留。

优先验证完整外部行为，不逐层 mock，也不为每个 helper 建测试。仅为固定 Pi 回调接缝、模型流、状态 codec、事件重建及复用组件接入补有限契约测试，不断言内部模块布局或复制实现逻辑。

### 测试先例与实施次序

- 后端沿用 unittest/fake Dify 的配对、预算、状态往返、权限和流转换经验，策略契约用实际 SDK；前端继承会话恢复、工具兜底和附件的行为先例，不把 AG-UI 编码断言移作新协议要求。
- 先验证 Vue 静态抽取与 Dify 事件穿透，再验证 Pi–Dify 模型/工具/状态并尽早做离线启动，随后扩展技能、预算、压缩、交互和异常恢复。这是风险验证次序，不缩减可靠性范围。
- 浏览器覆盖过程展示、展开、键盘问卷、提交防重复、刷新/切换、附件及断流；无推理或 partial 时仍准确显示运行状态。
- 实际 Dify 和两架构运行独立记证据，缺少环境保留未验证项，不用 fake、源码、上游测试或其他架构替代。未约定性能阈值时先给同条件对比，不宣称未经测量的提升。

## Out of Scope

- 全部官方 RPC、官方 Node 运行时、完整社区 Pi Web 后台、浏览器执行 Agent。

- 原生 Human Input 编排、Agent v2 AskHuman、额外网关、任意重放、多客户端原子锁或跨崩溃恰好一次承诺。
