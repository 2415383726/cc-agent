# 13: 工具审批、会话授权与策略重检

**What to build:** 工具需要授权时展示独立审批，用户刷新后可批准或拒绝原操作；批准仍遵守当前策略和预算。

**Blocked by:** [12 AskUser 问卷暂停与跨轮答复](12-ask-user-roundtrip.md)

**Status:** ready-for-agent

**Version:** v2；用户已确认拆分并发布。按必要前置完成情况选择实施前沿；当前尚未实施。

**Parent:** [Agent 工作台规格 v2](../spec.md)

**Spec coverage:** US27、US28、US29；V12、V13、V15。这是本票涉及的行为，不表示本票单独签收整个验收场景；最终平台证据由 17、18 补齐。

## Acceptance criteria

- [ ] 审批使用区别于普通 AskUser 的交互类型、稳定操作 ID、完整原参数与授权范围，问卷答案和普通聊天不能自动变为批准。
- [ ] 审批前不执行目标工具，同批尾部零真实执行；保存 pending、配对未执行结果并正常等待，不保持进程 Promise。
- [ ] 刷新/重建后展示同一待确认操作；参数或状态缺失、过大、过期时拒绝，不能重建为不同操作。
- [ ] 批准后使用当前身份重检工具存在、可见性、策略、会话授权和 10 的预算；已撤销权限或预算不足不得执行。
- [ ] 确认原操作未执行后才恢复；构造导入前有效会话投影，保持原 call ID 和唯一结果，不调用不存在的 replace API。
- [ ] 拒绝只产生明确结果不执行；会话授权范围可恢复但不绕过服务端权限，原批次尾部仍由后续模型决定，不自动重放。
- [ ] 批准/拒绝的重复、错误 ID、错误类型与取消均受控，页面清楚呈现等待、拒绝、实际执行及失败。
- [ ] 从策略到浏览器覆盖普通 Dify 工具批准/拒绝/权限变化/预算耗尽/保存失败，检查实际执行次数与合法会话；远程 MCP 组合由 14 扩展。

## Implementation context

- 依赖 12 已验证的 pending/gate/停止/交互路径，复用机制而保持问卷语义与授权语义分离，不把普通表单做成万能执行许可。
- 不得承诺仅凭插件状态实现跨崩溃 exactly-once；可确定未执行与 unknown 分开处理。
- 当前只有少量骨架和依赖导入，前置票是否完成须检查实际验收记录。v2 是唯一范围依据，不恢复旧 AG-UI 双入口、Tasks、六命令或旧前端兼容要求。
- 每票包含自身完整行为及必要验证，优先从策略入口、真实 SDK 消息和浏览器观察；只给易变接入点补有限契约测试，不为每个内部 helper 建测试。

## Verification

两个独立运行中提出和批准/拒绝同一操作，恢复前更改权限或预算并检查阻止效果；观察原 call ID、唯一结果和尾部未执行。
