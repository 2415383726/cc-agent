# 04: 双架构离线单包与基本问答启动

**What to build:** 将已可运行的 Pi 问答封装成按 amd64/arm64 区分的完整离线包，在干净目标运行环境安装后完成基本续聊。

**Blocked by:** [03 Pi 驱动问答与跨轮续聊](03-pi-dify-conversation.md)

**Status:** ready-for-agent

**Version:** v2；用户已确认拆分并发布。按必要前置完成情况选择实施前沿；当前尚未实施。

**Parent:** [Agent 工作台规格 v2](../spec.md)

**Spec coverage:** US40、US41、US43；V20、V21。这是本票涉及的行为，不表示本票单独签收整个验收场景；最终平台证据由 17、18 补齐。

## Acceptance criteria

- [ ] 锁定 Python 3.12 两架构完整运行依赖、资源、许可证、版本清单与校验和，包括实际 LangChain 等传递依赖。
- [ ] 分别生成 Linux amd64/arm64 插件构建物；每环境只安装对应一个 difypkg，无需预装 Node、额外 Pi 服务或在线下载依赖/代码/运行时。
- [ ] 检查打包后代码不依赖仓库内旧插件目录、本机虚拟环境或开发机绝对路径；构建工具可以联网准备依赖，目标安装/运行不能联网补齐。
- [ ] 在干净隔离环境、阻断公网依赖访问的条件下完成安装、启动、模型问答、状态写回和重建续聊；业务模型按授权可达测试端点提供。
- [ ] 两架构分别提供真实执行或等价目标运行证据，不能仅解析 wheels、模拟 import 或用 amd64 结果替代 arm64。
- [ ] 记录包体积、安装步骤、基础启动耗时与完整版本/校验信息；明确本票仅验收基础链路，完整功能包由 17、18 重新验收。
- [ ] 记录静态 Web 构建物与插件包的不同部署位置；不宣称 difypkg 自动托管前端，不要求部署 Node Web 后台。

## Implementation context

- 离线约束从基础问答即验证，避免功能完成后才发现依赖或插件执行器的安装路径不可用；后续新增依赖须持续遵守同一打包规则。
- 目标环境必须符合 Dify 插件执行器约定的 Python 版本。环境不可执行时保留未验证项，不把安装限制写成用户额外预装步骤来绕过要求。
- 当前只有少量骨架和依赖导入，前置票是否完成须检查实际验收记录。v2 是唯一范围依据，不恢复旧 AG-UI 双入口、Tasks、六命令或旧前端兼容要求。
- 每票包含自身完整行为及必要验证，优先从策略入口、真实 SDK 消息和浏览器观察；只给易变接入点补有限契约测试，不为每个内部 helper 建测试。
